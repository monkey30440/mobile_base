Station ID Navigation — Read-Only Design Investigation
======================================================

結論
----

在目前v0.1.0範圍內，最小custom gap是：

  Station ID -> validated canonical geometry_msgs/PoseStamped

導航執行、feedback、result、cancel、route-assisted BT與lifecycle都可繼續交給
現有Nav2 stack。

若使用者需要可直接操作的Station navigation入口，最小完整方向是Model B：
薄application/client wrapper使用現有resolver，再直接呼叫Nav2 NavigateToPose。
目前沒有證據要求custom action、Waypoint Follower或新的navigation server。


A. Native Nav2 Coverage
-----------------------

Repository基準：

- Dockerfile指定ROS 2 Jazzy並安裝ros-jazzy-navigation2與nav2_bringup。
- Navigation只註冊NavigateToPoseNavigator。
- Route-assisted BT由同一個NavigateToPose入口驅動。
- 本機host沒有ros2，且沒有running/built Compose container，因此無法直接執行
  ros2 interface show或列出實際binary package版本。Installed-package證據限於
  Dockerfile、HEAD package declarations與既有source/tests。

Requirement: Submit single pose goal
Nav2 native support: 完整
Custom gap: 無
Evidence: NavigateToPose goal原生接受PoseStamped與可選BT path。
Official: https://api.nav2.org/actions/jazzy/navigatetopose.html

Requirement: Execute navigation
Nav2 native support: 完整
Custom gap: 無
Evidence: BT Navigator接受goal，現有BT再呼叫Route Server與FollowPath。

Requirement: Feedback
Nav2 native support: 完整
Custom gap: 無
Evidence: 原生feedback含current pose、navigation time、ETA、recovery count、
          distance remaining。

Requirement: Success/failure result
Nav2 native support: 完整
Custom gap: 無
Evidence: 原生result含ROS action terminal status、Nav2 error_code與error_msg。

Requirement: Cancellation
Nav2 native support: 完整
Custom gap: 無
Evidence: ROS 2 action原生支援cancel；Jazzy CancelGoal定義cancel acceptance/rejection。
Official:
https://docs.ros.org/en/jazzy/How-To-Guides/Topics-Services-Actions.html
https://docs.ros.org/en/jazzy/p/action_msgs/srv/CancelGoal.html

Requirement: Simple application API
Nav2 native support: 完整
Custom gap: 僅application-specific input handling
Evidence: BasicNavigator.goToPose()、getFeedback()、getResult()、getTaskError()、
          cancelTask()已包裝ROS action細節。
Official: https://api.nav2.org/nav2-jazzy/html/md_nav2_simple_commander_README.html

Requirement: Multiple ordered poses
Nav2 native support: 完整
Custom gap: Station resolution仍需custom
Evidence: NavigateThroughPoses接受pose sequence，不接受Station ID。
Official: https://api.nav2.org/actions/jazzy/navigatethroughposes.html

Requirement: Waypoint task orchestration
Nav2 native support: 完整
Custom gap: Station resolution仍需custom
Evidence: Waypoint Follower接受pose array，並在每點執行task plugin。
Official: https://docs.nav2.org/configuration/packages/configuring-waypoint-follower.html

Requirement: Route-assisted navigation
Nav2/current stack support: 現有stack已提供
Custom gap: 無新增gap
Evidence: HEAD將route graph傳給Route Server，並將route-assisted BT設為
          NavigateToPose default。

Requirement: Planner/controller/recovery failure propagation
Nav2 native support: 完整
Custom gap: 不應重定義
Evidence: NavigateToPose result承載error code/message；BT設定列出compute/follow errors。

Requirement: Nav2 lifecycle bringup
Nav2 native support: 完整
Custom gap: Resolver若只是client，不需加入Nav2 lifecycle
Evidence: 現有lifecycle manager管理Nav2 servers；官方manager提供configure、activate、
          shutdown及bond監控。
Official: https://docs.nav2.org/tutorials/docs/adding_a_nav2_task_server.html

Requirement: Station ID -> pose
Nav2 native support: 沒有
Custom gap: 必須custom
Evidence: Jazzy navigation actions只有pose、poses、waypoints與GPS waypoints，沒有
          named station target。
Official: https://api.nav2.org/jazzy/actions/navigation/

Requirement: Station catalog loading
Nav2 native support: 沒有通用原生能力
Custom gap: 必須custom
Evidence: Waypoint Follower需要caller提供poses；不提供named station catalog。

Requirement: Station ID validation
Nav2 native support: 沒有
Custom gap: 必須custom
Evidence: Nav2收到的boundary已是PoseStamped。

Requirement: Catalog pose validation
Nav2 native support: 部分
Custom gap: catalog-specific validation需custom
Evidence: Nav2處理navigation/TF errors，但不理解catalog integrity或Station identity。

Requirement: Yaw scalar -> quaternion
Nav2 native support: 沒有Station-specific API
Custom gap: 必須custom或使用一般TF helper
Evidence: Nav2要求最終輸入PoseStamped，不負責catalog yaw schema。

Requirement: Unknown Station reporting
Nav2 native support: 沒有
Custom gap: 必須custom
Evidence: Nav2無法區分unknown Station與其他upstream input errors。

NavigateThroughPoses不補Station gap：

  PoseStamped[] -> ordered multi-pose navigation

不是：

  Station ID -> catalog lookup

用單一pose呼叫NavigateThroughPoses不會增加Station semantics，反而改變action與BT
navigator requirements。HEAD目前也只啟用navigate_to_pose navigator。

Simple Commander定位：

nav2_simple_commander.BasicNavigator是官方Python client facade，不是新navigation server。
它適合Model B，因為能提供：

- goToPose(pose)
- non-blocking feedback
- cancelTask()
- getResult()
- getTaskError()
- waitUntilNav2Active()

官方範例：
https://github.com/ros-navigation/navigation2/blob/main/nav2_simple_commander/nav2_simple_commander/example_nav_to_pose.py

但HEAD TargetAdmission是C++ library；若wrapper選Python，不能無成本直接link此library。
這是integration language問題，不是Nav2能力缺口。


B. Minimum Custom Responsibilities
----------------------------------

不可避免的custom responsibilities只有：

1. 載入Station catalog。
2. 驗證catalog結構與每筆Station資料。
3. 以明確規則查找Station ID。
4. 將Station平面pose轉為canonical geometry_msgs/PoseStamped。
5. 在送交Nav2前回報pre-navigation rejection：
   - empty/unknown Station ID
   - catalog unavailable/malformed
   - duplicate Station ID
   - non-finite position/yaw
   - invalid或非預期frame
6. 將有效goal header設為目前navigation global frame，現況為map。
7. 產生有效yaw quaternion。

不屬於custom resolver：

- path planning
- route selection
- controller execution
- costmap或collision handling
- recovery
- navigation feedback
- navigation action result
- navigation cancellation
- Nav2 lifecycle management

最小boundary：

  station_id
      |
      v
  Station Resolver
      |
      v
  validated canonical PoseStamped
      |
      v
  Nav2 NavigateToPose

Navigation execution可以完整留給Nav2。


C. Integration Model Comparison
-------------------------------

Model A — Thin ROS service

Flow:

  client -> ResolveStation service -> PoseStamped
         -> client -> NavigateToPose

Custom code: 小，但caller仍需Nav2 client。
Custom ROS interface: 一個custom service。
Nav2 reuse: 高。
Caller simplicity: 必須先resolve，再自行NavigateToPose。
Feedback/result: 來自第二次NavigateToPose call。
Cancel: caller直接cancel Nav2。
Testability: resolver service與navigation分開測。
Future fleet/task: resolver可被多client共用，但navigation orchestration散在caller。
Coupling: caller同時耦合custom service及Nav2 action。
Failure modes: resolve成功後navigation可能未送出；存在two-stage state。
Duplicate Nav2 capability: 不重複navigation，但service本身未必必要。
MVP/YAGNI: 只有多個獨立caller需要resolver時才合理。

Service只完成短期lookup，不能自然承載navigation feedback或cancel。它沒有消除
navigation client，只增加ROS round trip與custom interface。

Model B — Thin application/client wrapper

Flow:

  station_id -> local resolver -> PoseStamped
             -> native NavigateToPose client
             -> native feedback/result/cancel

Custom code: 最小完整垂直切片。
Custom ROS interface: 零新增interface。
Nav2 reuse: 最高。
Caller simplicity: CLI/application user最簡單。
Feedback/result: 直接透傳或呈現Nav2結果。
Cancel: 直接cancel Nav2。
Testability: pure resolver與action client可分層測試。
Future fleet/task: 適合單一operator/app；fleet若需直接ROS contract會較coupled。
Coupling: wrapper耦合Nav2 public API。
Failure modes: pre-navigation與navigation failure可清楚區分。
Duplicate Nav2 capability: 無。
MVP/YAGNI: 最符合。

可使用：

- C++ rclcpp_action，直接link現有C++ library；或
- Python nav2_simple_commander，但需要Python resolver implementation/binding。

Wrapper是Nav2 client，不是navigation server，不需加入Nav2 lifecycle manager。

Model C — Custom NavigateToStation action

Flow:

  Station ID -> project action server -> NavigateToPose action client

Custom code: 最大。
Custom ROS interface: custom action及message package。
Nav2 reuse: 高，但包裝一層。
Caller simplicity: remote ROS Station client最簡單。
Feedback/result: 必須proxy或重新映射。
Cancel: server必須正確轉發。
Testability: 需測action forwarding、cancel、preemption和terminal races。
Future fleet/task: 最穩定的project-level Station action contract。
Coupling: clients耦合project action，server耦合Nav2。
Failure modes: cancel/result forwarding、server restart、double terminal state。
Duplicate Nav2 capability: action lifecycle/feedback/result/cancel大量proxy。
MVP/YAGNI: 除非stable remote Station action是明確需求，否則過度。

Model D — Nav2 Waypoint Follower

Custom code: 中等，resolver仍不可少。
Custom ROS interface: 無project interface，但增加Nav2 server/action。
Nav2 reuse: 高。
Caller simplicity: 仍須把Station轉pose array。
Feedback/result: FollowWaypoints/current-waypoint/missed-waypoint semantics。
Cancel: cancel FollowWaypoints，再由它取消下游NavigateToPose。
Testability: 需測額外follower lifecycle/action。
Future fleet/task: 適合multi-waypoint及arrival task executor。
Coupling: Waypoint Follower再耦合NavigateToPose。
Failure modes: missed-waypoint、stop_on_failure、task executor failures。
Duplicate Nav2 capability: 對single goal重複NavigateToPose orchestration。
MVP/YAGNI: 不符合single Station requirement。

Waypoint Follower接受PoseStamped array，不接受Station ID；仍需要同一resolver。它內部
以NavigateToPose作client：
https://api.nav2.org/nav2-jazzy/html/classnav2__waypoint__follower_1_1WaypointFollower.html

對single Station使用length-one waypoint list只增加orchestration，沒有補Station identity。


D. Existing TargetAdmission Reuse Assessment
---------------------------------------------

值得保留：

- YAML file/string loading。
- exact Station ID lookup。
- empty/unknown ID rejection。
- unavailable/malformed catalog rejection。
- finite coordinate/yaw validation。
- yaw-to-quaternion conversion。
- canonical PoseStamped generation。
- expected-frame及normalized quaternion validation。
- structured AdmissionStatus及human-readable message。
- pure-library unit test surface。

Evidence：

- src/mobile_base_navigation/include/mobile_base_navigation/target_admission.hpp
- src/mobile_base_navigation/src/target_admission.cpp
- src/mobile_base_navigation/test/test_target_admission.cpp

它可直接作為最小custom resolver core，不需先變成ROS node。CMake已將它建立、install、
export為linkable library，所以C++ application/client可直接link/use。

Pure data transformation：

- Station ID查表。
- scalar yaw轉quaternion。
- Station record轉PoseStamped。
- finite value檢查。
- frame consistency檢查。
- catalog schema檢查。

這些不需ROS communication node。Library使用ROS message type和rclcpp::Time，不代表
必須是Node。

不應擴張或混入：

- Nav2 action orchestration本身。
- navigation feedback aggregation。
- result/error remapping。
- cancellation forwarding。
- Route Server選點。
- path/costmap validity判斷。
- obstacle/recovery policy。
- lifecycle management。

與Station-only MVP不完全一致之處：

1. TargetInput discriminator和GoalPoseTarget同時處理direct pose；Station resolver不需要
   統一兩種target。
2. admit_goal_pose(x,y,yaw_deg)是operator convenience transformation，不是Station
   resolution必要能力，也不是Nav2 navigation能力。
3. Catalog version與namespace被讀取但未驗證或runtime使用。
4. description不影響v0.1.0 Station navigation。
5. Duplicate ID目前由parsed_stations[entry.name] = entry靜默覆寫，不符合deterministic
   validation boundary。
6. Station catalog yaw目前按radians解讀，direct goal使用yaw_deg；unit contract必須明確。
7. Station output frame硬編碼map；與現況一致，但catalog contract應明示。


E. Minimal Station Catalog Contract
-----------------------------------

每筆Station最少只需要：

  station_id
  x
  y
  yaw

另有catalog-level invariant：

  frame_id = map

不需要：

- description
- namespace
- fleet ownership
- database key
- cloud metadata
- per-station task
- route node ID
- map UUID
- per-station frame
- quaternion四個components

Frame strategy：

v0.1.0最小contract應固定整份catalog為map frame，不應每筆重複保存frame。

理由：

- 現有Nav2 global frame是map。
- 現有resolver已輸出map。
- 每筆不同frame會引入TF availability、timestamp與transform policy。
- Station是map上的canonical destination，沒有mixed-frame requirement。

可由catalog-level frame_id: map明示，或由format固定；不需每筆重複。

Yaw representation：

Catalog只保存一個scalar yaw，由resolver產生normalized quaternion。不要讓catalog作者
手寫四元數，以免增加invalid combinations。

現有library與fixture使用radians，例如：

  yaw: 1.57079632679

若最大化現有core reuse，最小contract應明確規定yaw為radians。若human偏好yaw_deg，
這是可選contract decision，但不能同時允許兩種模糊格式。

YAML：

YAML足夠。v0.1.0是小型static catalog，沒有證據需要database、parameter server或cloud。
ROS parameter YAML不會自動提供Station schema、duplicate detection或PoseStamped construction；
改用parameters不會消除resolver。

Schema/version：

解析Station navigation所需的絕對最小資料不需要version。但若檔案包含version，resolver
必須驗證它，而不是只讀取後忽略。兩個一致MVP選項是：

- 不把version列入v0.1.0 contract；或
- 使用單一固定schema version並拒絕unknown version。

Repository無法決定哪個是產品需求，保留為human decision。

Validation timing：

- unreadable/malformed catalog、duplicates、missing fields、non-finite values：
  startup/load-time整體拒絕。
- empty/unknown Station ID：lookup-time拒絕。
- catalog validation失敗後：不可送NavigateToPose goal。
- duplicate Station ID：拒絕catalog，不能first-wins或last-wins。
- yaw：必須finite；轉換後quaternion必須normalized。
- invalid frame：catalog-level立即拒絕。
- unknown Station：pre-navigation error，不能轉成Nav2 generic failure。


F. Recommended Boundary
-----------------------

推薦architecture direction：

  Operator/application input: Station ID
                   |
                   v
        Pure Station Resolver Core
        - load/validate catalog
        - exact ID lookup
        - produce map-frame PoseStamped
                   |
         pre-navigation success
                   |
                   v
         Nav2 NavigateToPose client
                   |
                   v
     Existing route-assisted navigation stack

對v0.1.0推薦Model B：thin application/client wrapper。

理由：

1. 唯一同時完成user capability且不新增project ROS interface的model。
2. 現有TargetAdmission可作C++ resolver core。
3. Resolver output正好符合Nav2 native action boundary。
4. Feedback、result與cancel不需proxy或重新定義。
5. 現有route-assisted BT仍由NavigateToPose觸發。
6. Resolver failure與navigation failure保持兩個清楚階段。
7. 不需新server或lifecycle participant。
8. 未來若確認需要cross-process/fleet stable Station action，再評估Model A或C；目前
   requirement不足以預先引入。

推薦的是boundary與integration direction，不是implementation plan。

Canonical boundary為PoseStamped的原因：

- Nav2 NavigateToPose原生goal就是PoseStamped。
- 同時攜帶position、orientation、frame與timestamp。
- Route-assisted BT已從同一goal blackboard取pose。
- Planner、Route Server、controller不需知道Station identity。
- Station ID是application/domain identity；PoseStamped是navigation contract。
- 把Station ID傳入BT或Route Server會把catalog concern洩漏到navigation core。

加入Station ID後，現有證據不要求修改：

- Route Server
- route_assisted_nav.xml
- planner
- controller
- collision monitor
- base control
- localization
- lifecycle managers


G. What Must NOT Be Customized
------------------------------

應直接沿用Nav2/ROS 2 native capabilities：

- NavigateToPose action definition。
- Pose goal submission transport。
- Goal acceptance與goal handle。
- Navigation feedback。
- Success/abort/canceled terminal status。
- Nav2 error_code與error_msg。
- Action cancellation protocol。
- Planner、controller與recovery failure propagation。
- BT Navigator。
- Route Server與現有route-assisted BT。
- Costmaps、collision monitor與obstacle handling。
- ros2_control command chain。
- AMCL/localization。
- Nav2 lifecycle management。
- NavigateThroughPoses或Waypoint Follower，除非未來真的出現multi-stop/task-executor
  requirement。
- Custom NavigateToStation action，除非human明確要求remote stable ROS Station contract。
- Custom BT Navigator或Station-aware BT node。
- Custom navigation server。
- Project-specific navigation result/error taxonomy。

Failure responsibility：

  Pre-navigation errors
    -> Station resolver/application reports
       unknown station
       malformed/unavailable catalog
       duplicate ID
       invalid coordinates/yaw/frame

  Navigation errors
    -> Nav2 action reports directly
       goal rejected
       planning/route/controller failure
       TF/timeout
       recovery/obstacle failure
       canceled
       succeeded

Application可以顯示兩類結果，但不應把Nav2 error重新發明為project enum。


H. Open Questions
-----------------

以下需要human decision：

1. v0.1.0 Station入口只需operator CLI/application，還是任意remote ROS node都要能以
   Station ID呼叫？
2. Wrapper採C++直接重用TargetAdmission，還是Python使用nav2_simple_commander？
3. Station ID是否case-sensitive？現有implementation是exact、case-sensitive lookup。
4. Station ID允許哪些字元與命名格式？
5. Catalog yaw正式單位採現有radians，或改為operator較直觀的degrees？
6. Catalog需強制schema version，或v0.1.0完全不含version？
7. Navigation進行中再次提交Station ID時，語意是reject、cancel-and-replace，或Nav2
   same-action preemption？
8. Catalog load failure時，application立即退出，或保持運行但拒絕Station requests？
9. Catalog只在process startup載入，或v0.1.0需要runtime reload？目前無reload requirement。
10. Current Docker image實際安裝的Nav2/Nav2 Route binary version無法從repository鎖定；
    需在可用container中取得package version，才能解釋官方Jazzy package matrix與HEAD
    nav2_route使用間的provenance差異。

# V1 route NavigateToPose native completeness research

Research [#30](https://github.com/monkey30440/mobile_base/issues/30), parent [#18](https://github.com/monkey30440/mobile_base/issues/18), human decision [#25](https://github.com/monkey30440/mobile_base/issues/25). Date 2026-10-02. Only new requirements/approved decisions are authoritative; no old spec/map or project runtime was consulted. This is evidence and minimal candidates, not a selected architecture, complete BT, implementation plan or specification.

Baseline: Ubuntu24.04/Jazzy, differential drive, native local odometry and model TF from [#22](https://github.com/monkey30440/mobile_base/issues/22#issuecomment-5943788571), single-FL mapping artifacts from [#23](https://github.com/monkey30440/mobile_base/issues/23#issuecomment-5943908909), map_server/AMCL and Operator-owned usable-localization judgment from [#24](https://github.com/monkey30440/mobile_base/issues/24#issuecomment-5943964561). Navigation/Teleop exclusion remains Operator procedure. No automated localization quality/admission system is added. During research the user further confirmed [decision #25 comment](https://github.com/monkey30440/mobile_base/issues/25#issuecomment-5944045615): native independent dual obstacle sources, alternate legal graph route allowed when blocked, and local deviation may return to the current recomputed legal route; original-route identity is not required.

## Stable provenance and completeness criterion

All runtime source/tests below are Nav2 **1.3.13**, immutable commit [f4108e5b1c2bce804a1aa0c7be6673a8eb4a1501](https://github.com/ros-navigation/navigation2/tree/f4108e5b1c2bce804a1aa0c7be6673a8eb4a1501), the retrieved official [Jazzy release manifest](https://github.com/ros/rosdistro/blob/master/jazzy/distribution.yaml) version 1.3.13-1. Human-readable tag links resolve to that inspected commit. No newer main feature is assumed. Unit source evidence is not execution of these tests or physical proof.

Requirement → capability → responsibility: route-governed NavigateToPose(x,y,yaw) needs graph-route selection, lawful entry/exit connectors, normal tracking, necessary obstacle deviation with return, complete goal check and policy-preserving failure. There is a difference between (1) native computation/control primitives, (2) a configured workflow that intends this behavior, (3) runtime verification/enforcement of every allowed-departure/return condition, and (4) actual physical performance. Do not exchange these evidence classes.

## Graph and connectors: native integration is expressible

**CONFIRMED:** [ComputeRoute](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_msgs/action/ComputeRoute.action) returns graph route plus dense path for pose or node-ID requests. [GoalIntentExtractor](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_route/src/goal_intent_extractor.cpp) chooses graph endpoints and optionally considers costmap reachability; pruning can omit portions already passed. [PathConverter](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_route/src/path_converter.cpp) interpolates edges, optional corner arcs and final edge heading; it does not itself include an arbitrary target position/yaw outside the graph. Graph data must be prepared in the map frame and express the legal topology; corners/arcs are representation/feasibility choices, not permission for unrestricted shortcuts.

**CONFIRMED native composition capabilities:** registered [BT libraries](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_behavior_tree/CMakeLists.txt) include ComputeRoute, ComputeAndTrackRoute, their cancellation, GetCurrentPose, GetPoseFromPath, ArePosesNear and ConcatenatePaths alongside ComputePathToPose/FollowPath. [BT navigator](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_bt_navigator/src/bt_navigator.cpp) loads built-ins and [NavigateToPose](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_msgs/action/NavigateToPose.action) accepts a BT file. Native Sequence/Fallback/decorator control is sufficient to express optional connector branches, bounded recoveries and error branches without a new orchestration server.

Endpoint corner cases are source-confirmed:

- [GetPoseFromPath](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_behavior_tree/plugins/action/get_pose_from_path_action.cpp) fails for an empty path or invalid index, supports first/last negative indexing and fills a missing pose frame from the path. These failures must not be classified as a successful omitted connector.
- [ArePosesNear](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_behavior_tree/plugins/condition/are_poses_near_condition.cpp) measures XY only. Same-position target yaw mismatch does not make orientation responsibility disappear. It may also return false on failed TF; a guard cannot interpret every false as valid geometry.
- [ComputePathToPose BT](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_behavior_tree/plugins/action/compute_path_to_pose_action.cpp) supports explicit start. In 1.3.13 supplying start without use_start uses that start; true use_start without valid start falls back to current pose. Intended last-connector start must actually be supplied.
- [ConcatenatePaths](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_behavior_tree/plugins/action/concatenate_paths_action.cpp) succeeds with either input nonempty and fails when both are empty; it concatenates poses rather than generating collision-free geometry, validating frames or adding a new final yaw. Input path freshness, common frame and junction consistency belong to integration validation.
- Native [Navfn](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_navfn_planner/src/navfn_planner.cpp) handles identical XY with a one-pose path whose orientation is the requested goal orientation when different, unless use_final_approach_orientation is true. It appends/replaces the terminal goal orientation for ordinary plans. Therefore always evaluating the final connector, including a zero-distance orientation-only connector, is a native candidate; no custom yaw runtime gap is inferred. Planner positional tolerance must remain consistent with product goal tolerance, especially occupied/unreachable goals.
- [SimpleGoalChecker](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_controller/plugins/simple_goal_checker.cpp) checks xy and yaw tolerances, optionally statefully. Final controller goal must be the requested goal pose, not the route-end heading. Finite tolerances need physical calibration, not exact equality claims.

[Connector action tests](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_behavior_tree/test/plugins/action/test_compute_path_to_pose_action.cpp), [concatenation tests](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_behavior_tree/test/plugins/action/test_concatenate_paths_action.cpp) and [pose extraction tests](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_behavior_tree/test/plugins/action/test_get_pose_from_path_action.cpp) support primitive behavior. No shipped 1.3.13 [route-composite tree](https://github.com/ros-navigation/navigation2/tree/1.3.13/nav2_bt_navigator/behavior_trees) was found. The [modern official route-tree description](https://docs.nav2.org/jazzy/getting_started/nav2_behavior_trees/trees/navigate_on_route_graph_w_recovery/) is useful explanatory evidence but must be reconciled with pinned ports/control semantics; its presence under a Jazzy URL does not establish a released full workflow.

**Completeness result:** native graph/connector/final-pose composition is an available configuration/BT responsibility. Whole-tree software correctness remains UNRESOLVED pending integration evidence; absent shipped example alone is not a confirmed custom-runtime gap.

## Route tracking, detour and controller alternatives

[ComputeAndTrackRoute](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_msgs/action/ComputeAndTrackRoute.action) reports graph progress and rerouting, not trajectory control. [RouteTracker](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_route/src/route_tracker.cpp) recognizes nodes with radius/bisector progress conditions and generous boundary radii. This permits reasonable controller deviation but is not a proof that the robot stayed on every edge or returned after every detour. Route-tracker success also is not complete final x/y/yaw achievement.

[Route collision operation](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_route/src/plugins/route_operations/collision_monitor.cpp) flags blocked edge IDs and requests graph rerouting or fails tracking; [CostmapScorer](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_route/src/plugins/edge_cost_functions/costmap_scorer.cpp) can reject/cost graph edges. These are different from traversing around a local obstacle off graph and returning. Immediate invalidation/rerouting on any collision can suppress a feasible native local detour; configuration must preserve whichever policy is human-approved.

| Native controller | CONFIRMED capability in pinned source | Completeness boundary |
|---|---|---|
| MPPI | [Optimizer](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_mppi_controller/src/optimizer.cpp) samples/optimizes trajectories and throws NoValidControl after bounded retries. [PathAlignCritic](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_mppi_controller/src/critics/path_align_critic.cpp) permits reduced alignment pressure when path occupancy is high; native path/obstacle/goal critics and differential-drive model support dynamic avoidance | Native local detour candidate. Finite soft costs and horizon do not guarantee necessary-only departure or a later return postcondition. [PathHandler](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_mppi_controller/src/path_handler.cpp) nearest-point search/pruning can skip path prefixes; it does not prove edge traversal |
| DWB | [DWBLocalPlanner](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_dwb_controller/dwb_core/src/dwb_local_planner.cpp) evaluates sampled legal trajectories and weighted critics; no legal trajectory throws. [PathDist](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_dwb_controller/dwb_critics/src/path_dist.cpp), [PathAlign](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_dwb_controller/dwb_critics/src/path_align.cpp) and [BaseObstacle](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_dwb_controller/dwb_critics/src/base_obstacle.cpp) express path preference/obstacle rejection | Native differential-drive local avoidance candidate; weighted path costs are not a necessary-only departure or mandatory-return monitor; local horizon and trap behavior require evidence |
| RPP | [RegulatedPurePursuit](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_regulated_pure_pursuit_controller/src/regulated_pure_pursuit_controller.cpp) follows lookahead curvature, regulates speed and throws collision-ahead error; can rotate to target heading | Good native tracking candidate but not itself an alternative-trajectory obstacle detour optimizer. Alone it does not supply the required local off-route avoidance; another confirmed responsibility would be needed |

MPPI and DWB are viable native avoidance candidates; source alone cannot choose a winner on this AMR. RPP's lack of autonomous detour construction is a software responsibility distinction, whereas MPPI/DWB actual obstacle success is a hardware-performance question. Increasing critic weights or changing lookahead cannot be treated as formal route-policy enforcement. Corner smoothing and tracking corridor calibration are legitimate geometry/performance questions; a perfectly coincident mathematical line is not a physically attainable invariant and was not specified by the user.

## What can and cannot be concluded about strict policy

**CONFIRMED native intended workflow candidate:** graph-derived reference route + legal endpoint connectors + native local controller with obstacle/path objectives, keeping the route reference while detouring; bounded native failures with no whole-trip freespace fallback. This is substantially smaller than an added route-orchestration service. It expresses an intention to follow and return; it does not by itself prove compliance.

**CONFIRMED evidence limitation:** inspected path critics, SimpleGoalChecker, SimpleProgressChecker and RouteTracker do not implement a combined predicate: departure was required by obstruction, and every detour rejoined the allowed route before any unrestricted continuation. [SimpleProgressChecker](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_controller/plugins/simple_progress_checker.cpp) checks displacement over time, so a robot moving away indefinitely can keep satisfying progress; it is not monotonic graph progress or a return deadline. [IsPathValid](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_behavior_tree/plugins/condition/is_path_valid_condition.cpp) checks planned-path validity, not actual trajectory compliance. Goal reachability alone is insufficient evidence.

**CONFIRMED HUMAN SEMANTICS:** the user permits an alternate legal graph route and return to the current recomputed route; original-route identity is not required. **UNRESOLVED HUMAN acceptance detail, not a tuning choice:** what observable trajectory deviation counts as normal tracking versus an obstacle detour. The current requirement specifies physical route behavior and failure if compliant navigation cannot complete; it does not separately require a software corridor/return-deadline monitor. Lack of a formal guarantee in a native optimizer therefore does not establish a custom-runtime requirement. A native route-derived path with a local controller that temporarily deviates then resumes that path is a minimal candidate whose return behavior needs physical acceptance evidence. If strict runtime postcondition is confirmed, the unmet responsibility in the inspected native set is route-conformance/obstacle-departure/return supervision, not route search or motion control. A minimal native extension/plugin would be a candidate only for that precisely confirmed predicate, reusing native planning/control/failure. No new server, generic mode manager or custom planner is justified from current evidence; no full plugin design is produced here.

For the approved alternate-legal-route policy, native route recomputation/progress can be reused but cannot silently permit off-graph shortcuts. A stricter original-route-only policy would need different evidence; it is not the chosen V1 requirement. The approved variant does not allow an unrestricted ComputePathToPose fallback from robot to final target to substitute for the route segment. Endpoint connectors remain a distinct allowed responsibility; they cannot silently grow to cover the whole trip and erase network use.

## Failures and cancellation

**CONFIRMED:** native route actions have no-route/TF/graph/time errors; controller server rejects invalid path/controller, fails missing TF, waits only configured time for current costmap, throws progress/control errors and terminates actions ([controller server](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_controller/src/controller_server.cpp)). `failure_tolerance=-1` allows indefinite controller error patience; default movement-progress is not total task timeout. Bounded product failure must not be inferred while configuring unlimited retries/time tolerance.

[BT action nodes](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_behavior_tree/include/nav2_behavior_tree/bt_action_node.hpp) translate aborted results to failure; halt cancels active child goals and waits for results with a bounded cancel timeout. [RecoveryNode](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_behavior_tree/plugins/control/recovery_node.cpp) provides finite retries. [BtActionServer](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_behavior_tree/include/nav2_behavior_tree/bt_action_server_impl.hpp) halts all actions, aggregates configured error-code blackboard names and maps BT success/failure/canceled to action terminal handling. Any optional-connector success branch must not swallow actual planner/control failure. Concurrent route tracking must be canceled when path tracking/task terminates; neither tracker success alone nor controller arrival alone proves all required phases. Pure clear/wait/retry recovery does not authorize freespace-policy escape. Successful ROS cancellation/zero velocity is software evidence; physical stop remains hardware evidence.

## Two independent obstacle scan sources

**CONFIRMED native capability:** [ObstacleLayer](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_costmap_2d/plugins/obstacle_layer.cpp) iterates independent observation_sources, creates a subscriber/TF filter/buffer per LaserScan source and supports separate marking/clearing/range settings. [ObservationBuffer](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_costmap_2d/src/observation_buffer.cpp) transforms each observation's origin from sensor_frame or its message frame at the data timestamp and retains the origin for ray clearing. Unlike virtual-scan input, two physical sources need not share a synthetic origin or scan identity. Mapping/AMCL's selected single-FL source does not limit costmap inputs.

Boundaries: missing/invalid TF prevents processing; infinity treatment depends on inf_is_valid (positive infinity can be converted to just below maximum range). Marking/clearing depends on sensor validity and geometry. observation_persistence and expected_update_rate must be configured knowingly: expected_update_rate=0 makes isCurrent always true; freshness tracks received/buffered update time, not independent proof of correct clock or measurement. Projection tries high-fidelity transform and can fall back to ordinary projection on TF exception. These source mechanisms do not prove complete deskew, all-world coverage, collision safety or useful physical stopping distance. Per-source frames/time/extrinsics and self-occlusion remain hardware validation/calibration responsibilities. No merger is needed to fulfill this native two-source obstacle-input responsibility.

## Bounded handoff

**CONFIRMED:** stable native graph, endpoint/yaw handling, BT integration and action failure/cancel primitives; MPPI/DWB local avoidance candidates; two independent obstacle inputs. **UNRESOLVED:** whole selected workflow integration evidence, physical route/return acceptance details and controller selection. Approved alternate-route and independent-dual-input semantics are confirmed. No hard unmet native computational responsibility or custom runtime requirement is established for the currently stated workflow; formal automatic route-policy supervision would be an additional confirmed requirement before a plugin is justified. **REQUIRES HARDWARE VALIDATION:** actual normal-route behavior, obstacle-driven departure and actual return, graph intersections/loops without shortcuts, unavailable-detour failure, final pose and physical cancel/stop on this AMR. **REQUIRES CALIBRATION:** footprint/extrinsics/time, dynamics, trajectory horizon/corridor and return/goal tolerances. Physical tuning uncertainty is not a custom-code gap.

No tests executed or new infrastructure created. Existing Docker software validation later should cover empty/trivial route, absent/zero connectors, target yaw with coincident XY, TF/frame failures, obstacle detour and return/alternate-route policy, no route/unreachable final connector, error propagation, bounded inability-to-progress and cancel of concurrent actions. Unit/replay tests can establish software composition; observed AMR trajectories are required for physical behavior. Research #30 may close with these findings; decision #25 remains human-owned and map is not cleared by this note.

# V1 dual picoScan150 Mapping input research

Ticket [#29](https://github.com/monkey30440/mobile_base/issues/29), parent map [#18](https://github.com/monkey30440/mobile_base/issues/18), Mapping decision [#23](https://github.com/monkey30440/mobile_base/issues/23). This research resolves input evidence only; it selects no architecture. Date: 2026-10-02. Authority: new V1 requirements and [confirmed hardware decision #22](https://github.com/monkey30440/mobile_base/issues/22#issuecomment-5943788571). Two physical picoScan150 sources are FL/BR, distinct frames `base_lidar_link_FL` and `base_lidar_link_BR`, native sick_scan_xd. robot_localization owns odom→logical footprint; model TF belongs to robot_state_publisher. No existing spec, old map or project-owned runtime was used. No downstream localization/navigation/bringup design is introduced.

The Mapping requirement is Teleop mapping and saving a reusable map. It does not require both scanners simultaneously. User discussion has confirmed slam_toolbox map→odom ownership and map.pgm + map.yaml artifacts; this note investigates whether its input responsibility can be native, not whether to replace that confirmed owner.

## slam_toolbox: one topic is not the decisive limit

**CONFIRMED:** pinned [common source](https://github.com/SteveMacenski/slam_toolbox/blob/2.8.5/src/slam_toolbox_common.cpp) configures one `scan_topic` and one LaserScan subscriber, filtered for TF to odom. It is not a configurable list of independent scan subscriptions. Multiple native publishers/relays could deliver individual messages to one topic; [topic_tools Relay](https://github.com/ros-tooling/topic_tools/blob/1.3.4/README.md) provides native generic message republishing without constructing a virtual scan. Thus absence of a topic list alone is not proof of a multi-sensor gap.

**CONFIRMED source-level blocker for unmodified dual-source interleaving:**

1. `getLaser()` caches metadata by each message's `header.frame_id`, then adds its LaserRangeFinder to the dataset with `overrideSensorName=true` ([common source](https://github.com/SteveMacenski/slam_toolbox/blob/2.8.5/src/slam_toolbox_common.cpp)).
2. `LaserAssistant::makeLaser()` creates every device with the same Karto name **Custom Described Lidar**, although it reads each sensor's TF offset and scan geometry ([laser_utils.cpp](https://github.com/SteveMacenski/slam_toolbox/blob/2.8.5/src/laser_utils.cpp)). No subsequent per-frame rename was found in these paths.
3. Karto `Dataset::Add()` and `SensorManager::RegisterSensor()` map sensors by that name; override replaces the registered pointer. `LaserRangeScan::GetLaserRangeFinder()` resolves its sensor by name; `GetSensorAt()` uses that registered offset ([Karto.h](https://github.com/SteveMacenski/slam_toolbox/blob/2.8.5/lib/karto_sdk/include/karto_sdk/Karto.h), especially RegisterSensor, Dataset::Add, GetLaserRangeFinder and GetSensorAt).
4. `getLocalizedRangeScan()` stores `laser->GetName()`, not an independent frame identity. Karto Mapper scan managers and sequential matching also key on sensor name ([Mapper.cpp](https://github.com/SteveMacenski/slam_toolbox/blob/2.8.5/lib/karto_sdk/src/Mapper.cpp)). Consequently, registering the second physical frame can substitute its geometry/extrinsics for scans of the first and conflates scan histories. Distinct ROS frame IDs in a common topic do not fix this underlying name collision.

This is a confirmed software semantic limitation of the pinned implementation; it does not require guessing map quality or assuming a missing test implies custom code. Same-topic native relaying can fulfill transportation responsibility but **cannot fulfill correct independent dual-device identity** here. A hypothetical upstream fix would have to address identity, registration/history and gates; this note does not authorize a project fork or prescribe a patch.

**CONFIRMED additional cross-source limits:** `shouldProcessScan()` in common source has shared static last pose/time, scan counter and minimum time/movement gates, not per-device gates. The second scan at the same timestamp may be filtered after the first; source rates and callback order affect accepted measurements. [Synchronous source](https://github.com/SteveMacenski/slam_toolbox/blob/2.8.5/src/slam_toolbox_sync.cpp) queues admitted scans FIFO, while [asynchronous source](https://github.com/SteveMacenski/slam_toolbox/blob/2.8.5/src/slam_toolbox_async.cpp) processes admitted callbacks directly; neither path establishes a two-source time-ordered collator or fairness guarantee. Both estimate odometry at the scan header timestamp. Range conversion consumes range arrays, not per-beam `time_increment` for deskew ([laser_utils.hpp](https://github.com/SteveMacenski/slam_toolbox/blob/2.8.5/include/slam_toolbox/laser_utils.hpp)). “Synchronous mode” means its processing queue, not physical synchronization of the two scanners.

The pinned [test directory](https://github.com/SteveMacenski/slam_toolbox/tree/2.8.5/test) and [launch/config examples](https://github.com/SteveMacenski/slam_toolbox/tree/2.8.5/launch) inspected contain no identified dual-physical-scanner acceptance example. This is bounded evidence coverage, not a separate confirmed runtime gap.

## Native candidate A: one physical scanner for Mapping

Requirement → capability → responsibility → native completeness: create/save a useful map → 2D SLAM from a physical scan and local odometry → slam_toolbox processes one selected physical source with its real frame/origin → **CONFIRMED native functional capability**; input configuration selects FL or BR, without a merger or custom runtime. The other scanner remains separately available through its native driver; this does not require removing it from the hardware architecture.

In the single-device case, Karto occupancy `AddScan()` raytraces from the actual `GetSensorPose()`, with sensor offset supplied by TF ([Karto.h](https://github.com/SteveMacenski/slam_toolbox/blob/2.8.5/lib/karto_sdk/include/karto_sdk/Karto.h)). This avoids inventing a central virtual ray origin. Lack of simultaneous dual scans is not a V1 functional requirement gap. **REQUIRES HARDWARE VALIDATION:** selected scanner's actual field of view, self-occlusion, environmental geometry, operator traversal and loop closure must produce a sufficiently complete/useful map. Neither selecting FL nor BR is justified as superior without evidence. Actual input timestamps, valid odometry/TF, movement speed and scan distortion also require physical evidence. These validation items do not retroactively establish that a merger was required.

## Native candidate B: released upstream virtual-scan merger

**CONFIRMED native availability, bounded semantics:**

- [scan_2d_merger 2.1.0 source](https://github.com/ali-pahlevani/2D_Scan_Merger_ROS2/blob/2.1.0/src/scan_2d_merger/src/scan_2d_merger.cpp) buffers topic inputs, chooses timestamps within a tolerance, projects finite valid endpoints using TF into one output frame, keeps the nearest range per polar bin, fills empty bins with infinity or range_max + epsilon, writes the first selected source's timestamp and sets `time_increment=0`. Transforms use latest TF; static transform caching is appropriate only for fixed geometry. Its `moving_frames` option refreshes TF and is not per-ray deskew or robot-motion alignment between acquisition times. An upstream [test file](https://github.com/ali-pahlevani/2D_Scan_Merger_ROS2/blob/2.1.0/src/scan_2d_merger/test/test_scan_merger.cpp) exists; it does not constitute validated AMR map quality.
- [dual_laser_merger 0.3.1 source](https://github.com/pradyum/dual_laser_merger/blob/0.3.1/src/dual_laser_merger.cpp) uses ApproximateTime for two scan inputs, projects/combines point clouds, optionally filters points, then produces a single-frame polar scan with `time_increment=0`. The released code also contains an optional averaging loop with inclusive `<= ranges.size()` indexing; do not treat every optional feature as verified. Its emitted clouds/scans do not carry independent ray-origin histories into slam_toolbox.
- [pointcloud_to_laserscan 2.0.2 source](https://github.com/ros-perception/pointcloud_to_laserscan/blob/2.0.2/src/pointcloud_to_laserscan_node.cpp) is a native cloud-to-polar conversion, not a multi-source synchronizer: height/range/angle filtering, nearest endpoint per bin, configurable empty-bin infinity and `time_increment=0`. Adding cloud conversion alone does not close origin/time semantics. ROS1 ira_laser_tools familiarity is not stable-Jazzy capability evidence; released ROS2 candidates above are stronger provenance.

**CONFIRMED semantic tradeoff:** the [LaserScan definition](https://github.com/ros2/common_interfaces/blob/137e97dc5ec724b78cdbaa3b89927c3c29f81f02/sensor_msgs/msg/LaserScan.msg) represents one planar scan frame and first-ray time with a uniform per-ray time increment; it has no per-ray sensor origin/identity. Reprojecting endpoints to a virtual origin changes the ray segments. A return visible from FL can have an occluded line from the virtual center; polar binning cannot establish that center→return space was observed free. Nearest-bin selection discards farther endpoints; invalid/no-return/unsampled/out-of-view bins become conflated after finite-point filtering and empty-bin filling.

Pinned Karto ignores `range <= minRange`, `range >= maxRange` and NaN in occupancy carving; finite returns between threshold and maximum can trace free space without marking the endpoint, while infinity is beyond maximum and ignored ([Karto.h AddScan](https://github.com/SteveMacenski/slam_toolbox/blob/2.8.5/lib/karto_sdk/include/karto_sdk/Karto.h)). Therefore empty-bin infinity is not proof of observed free space; alternative finite fill values can change downstream behavior. Even ignoring unknown bins does not restore the correct physical origin for accepted finite returns. These are software semantics, not a claim that a virtual scan can never make a useful map.

Candidate completeness: released mergers fill slam_toolbox's one-device input shape and aggregate dual endpoints, but **do not preserve all physical ray-origin, no-return and temporal semantics**. Whether an explicitly accepted approximation satisfies map quality is **REQUIRES HARDWARE VALIDATION**. Approximate timestamp pairing is not deskew; avoid assigning complete origin-faithful measurement responsibility to these conversions. No custom merger is established as necessary.

## Native multi-laser SLAM comparison, without selection

**CONFIRMED:** Jazzy-released Cartographer ROS [node.cpp](https://github.com/ros2/cartographer_ros/blob/2.0.9003/cartographer_ros/src/node.cpp) supports `num_laser_scans` and repeated `scan_1`, `scan_2` inputs with distinct sensor IDs. [sensor_bridge.cpp](https://github.com/ros2/cartographer_ros/blob/2.0.9003/cartographer_ros/src/sensor_bridge.cpp) transforms each source to tracking coordinates, records its origin and subdivides scans with timestamps. Native [range-data collator](https://github.com/ros2/cartographer/blob/2.0.9004/cartographer/mapping/internal/range_data_collator.cc) retains per-source origins and per-point times while cropping/merging and sorting temporal overlap; it can drop early points. [collator tests](https://github.com/ros2/cartographer/blob/2.0.9004/cartographer/mapping/internal/range_data_collator_test.cc) bound upstream software evidence.

Do not overclaim origin fidelity through the entire 2D occupancy pipeline: [local trajectory builder](https://github.com/ros2/cartographer/blob/2.0.9004/cartographer/mapping/internal/2d/local_trajectory_builder_2d.cc) motion-compensates points and uses each source origin to classify ranges/misses, then accumulates into one RangeData with a single final tracking origin. [2D probability-grid inserter](https://github.com/ros2/cartographer/blob/2.0.9004/cartographer/mapping/2d/probability_grid_range_data_inserter_2d.cc) casts rays from that accumulated origin. Thus it is a mature native multi-input/time-processing alternative, not proof of exact independent-origin occupancy carving. This comparison alone does not override the already confirmed slam_toolbox owner or design another localizer.

## Decision input and evidence boundary

| Candidate | Native complete responsibility | Confirmed limits / follow-up |
|---|---|---|
| One physical source → unmodified slam_toolbox | Single-device 2D Mapping and real-origin scan input | No functional dual-use requirement gap; selected sensor coverage/map quality require hardware evidence |
| Two separate scans interleaved → unmodified slam_toolbox 2.8.5 | Native transport possible via remap/Relay | Same Karto name/override causes device identity collision; shared gates/order and no per-beam deskew. Not demonstrated correct dual-device input |
| Released merger → slam_toolbox | Multiple endpoints adapted to one LaserScan | Virtual origin, invalid/unknown distinction and time approximation; actual quality must be explicitly validated |
| Native multi-laser Cartographer | Distinct input IDs, source/time collator and point motion compensation | Different SLAM owner if chosen; 2D insertion still single accumulated origin; no solution selection here |

Native-first bounded recommendation for decision #23: single-source Mapping is the smallest **already supported functional candidate** when simultaneous dual use is not required. If dual use is desired, explicitly evaluate whether released-merger approximation is acceptable; do not claim same-topic delivery automatically gives correct native dual-sensor slam_toolbox. A precise dual-input unmet responsibility must be confirmed before considering any upstream fix/project-owned adaptation. Missing physical quality evidence is a validation item, not permission to invent custom runtime.

**UNRESOLVED:** which physical scanner and accepted input approximation (if any) the human chooses; full target binary/configuration integration. **REQUIRES HARDWARE VALIDATION:** actual timestamps/data validity, scan/drop acceptance across motion, self-occlusion and environmental coverage, map artifacts after teleop traversal, no false clearing/ghost geometry and actual useful saved map. **REQUIRES CALIBRATION:** physical FL/BR extrinsics, scan planes, clocks/time offsets and odometry/scan-motion effects; nominal URDF is not calibration evidence. A software message replay could check identity/drop/ordering and conversion edge cases via existing Docker validation, but was not performed. No code tests, hardware validation, calibration, runtime edits or specification artifacts were produced. This research closes factual investigation only; decision #23 and the map remain open.

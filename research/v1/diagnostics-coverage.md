# Selected V1 Diagnostics coverage and minimal gaps

Research [#31](https://github.com/monkey30440/mobile_base/issues/31), input to human [decision #26](https://github.com/monkey30440/mobile_base/issues/26), authority [new map #18](https://github.com/monkey30440/mobile_base/issues/18). Checked 2026-10-02 (session environment). This supplements [research #21](https://github.com/monkey30440/mobile_base/blob/c3f1d5da17ac17564a636306f02b694aaa82bcdd/research/v1/diagnostics-bringup.md); representation, updater, aggregator expected/missing/stale and native lifecycle evidence are reused, not revalidated.

Selected architecture comes from closed new decisions [platform #22](https://github.com/monkey30440/mobile_base/issues/22), [Mapping #23](https://github.com/monkey30440/mobile_base/issues/23), [Localization #24](https://github.com/monkey30440/mobile_base/issues/24), [Navigation #25](https://github.com/monkey30440/mobile_base/issues/25). No existing production spec, old map or project-owned runtime was used. M1/USB IMU adapters are not implemented by this research; the IMU is redesigned and reference experience does not certify that redesign.

## Evidence basis and responsibility

Pinned inspected sources: sick_scan_xd **3.9.0**, robot_localization **3.8.3**, robot_state_publisher **3.3.4**, slam_toolbox **2.8.5**, Nav2 **1.3.13** (commit `f4108e5b1c2bce804a1aa0c7be6673a8eb4a1501`), diagnostics **4.2.7**, ros2_control **4.48.1**, ros2_controllers **4.42.1**. Native troubleshooting tools were checked against current Jazzy geometry2 **0.36.23** and ros2cli **0.32.12** release tags; [Jazzy release metadata](https://github.com/ros/rosdistro/blob/9cca73049e6c6b941fa8fca3a33229acaededdfe/jazzy/distribution.yaml) is version provenance, not an installed-system claim.

V1 requires important current abnormalities to identify component, basic cause/state and necessary troubleshooting information. It does **not** require every native error to become DiagnosticStatus, a new UI, remote history, automatic localization qualification or a diagnostics-controlled motion/readiness gate. Accordingly an attributable native log, service result, action error, lifecycle state or current-topic tool can cover a responsibility if its operational presentation lets the user answer the required questions. A combined topic containing every fault is not assumed.

## Current-topic / TF tools versus automatic diagnostics

Native `ros2 topic info/echo/hz` provides source graph, sample fields and received-rate investigation. `hz` measures this observer subscription, which is affected by QoS/resource conditions; it does not prove publisher or physical sampling rate, validate sensor content, or autonomously publish fault status. In its released implementation, no new samples means no updated hz statistics, not a new normalized stale-fault entry. [Jazzy topic guide](https://docs.ros.org/en/jazzy/Tutorials/Beginner-CLI-Tools/Understanding-ROS2-Topics/Understanding-ROS2-Topics.html), [hz 0.32.12](https://github.com/ros2/ros2cli/blob/0.32.12/ros2topic/ros2topic/verb/hz.py).

Native `tf2_echo`, `tf2_monitor` and `view_frames` support transform availability, age/rate and tree diagnosis; configured consumers also emit TF failure context. These are current troubleshooting tools, not a project-wide automatic readiness gate. [Jazzy TF introduction](https://docs.ros.org/en/jazzy/Tutorials/Intermediate/Tf2/Introduction-To-Tf2.html), [tf2_monitor source](https://github.com/ros2/geometry2/blob/0.36.23/tf2_ros/src/tf2_monitor.cpp).

The inspected mature native facilities provide topic/TF observer primitives or operator tools. No claim is made that there is a complete preconfigured arbitrary-robot ROS2 health monitor. If HITL requires automatic always-on report of the selected published scan's stalled/invalid timestamp state independent of consumers, the confirmed representation gap is narrowly **observe selected output arrival/stamp with device identity and configured policy**; first reuse native updater topic/timestamp tasks and suitable existing publisher/consumer checks. That conditional responsibility is not yet an approved runtime design. A generic graph-health FSM, duplicated component states or remote backend is not justified.

## Core context versus optional detail

Core information: attributable component/instance, basic observed cause/state, whether input/output is missing/stale/invalid or a native operation failed, and the relevant endpoint/topic/frame/drive/file or native error needed to investigate. Exact raw register/packet dumps, every timing percentile, historical trend storage, GPU-engine inventory and full debug logging are not mandatory by default. Diagnostic severity must describe evidence, not infer health from silence or create new control authority.

Use expected/stale aggregator configuration only for actual diagnostic producers (controller manager, enabled estimator/host/device-adapter checks, etc.). Requiring a fictitious picoScan updater heartbeat would report permanent missing status. Aggregator can detect a dead diagnostic producer, but a live producer with stale data needs its own relevant check. Native logs/action/service outputs remain legitimate evidence channels. Missing localization before the approved Operator initialization and navigation pending activation are legal states; transport/data/TF faults affecting expected capabilities remain reportable.

## Evidence classes and decision inputs

- **CONFIRMED:** pinned native outputs/boundaries above; meaningful transport/parse errors, map/action failures and current runtime resource/status tooling; picoScan generic updater exclusion; conditional costmap freshness; adapter-local device reporting responsibility already implied by #22. This is source/API inspection, not implemented coverage.
- **UNRESOLVED:** final Diagnostics presentation/operator workflow; actual target identifiers/protocol registers; precise policies for important freshness/timestamps and host resources; whether any required ongoing selected-output check is not covered by accepted native logs/consumers/operator tools. No independent all-native end-to-end completeness claim is made. These can be clarified in #26 without inventing runtime first.
- **REQUIRES HARDWARE VALIDATION:** dual IP/UDP/source identity, device unplug/disconnect/CRC/packet loss and live-receiver/no-scan cases; adapter communication/device fault semantics; TF/covariance sample correctness; map workflow and task error presentation; host monitoring on Jetson/container; sensor invalid/no-return behavior and physical sensor obstruction; operator fault identification. Native success/heartbeat does not prove physical functionality.
- **REQUIRES CALIBRATION:** sensor/odometry/extrinsic/time properties and measured operating freshness tolerances when protocol values do not define them. Host threshold choices are operating-policy tuning, not sensor calibration. Do not invent values from process liveness.

Minimum current candidate: component-native diagnostics/status/results/logs plus native observer tools; selected host monitors; necessary M1/USB IMU adapter checks nearest to device evidence; project configuration preserves identity, enables applicable checks and maps meaningful operator context. Consolidated current diagnostics use native aggregation where producers exist. No new broad diagnostics manager, localization checker, control gate, custom UI or historical server is evidenced as necessary. Exact adoption/acceptance remains human decision #26.

No source/runtime modification, local software test execution, hardware validation or calibration was performed. Existing #21 source evidence was reused without claiming stronger verification. Later approved configuration/software checks must use repository Docker/package mechanisms and reuse applicable approved evidence before new validation.

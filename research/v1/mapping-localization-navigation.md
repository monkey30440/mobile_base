# V1 research: Mapping, Localization and route-based NavigateToPose

Research ticket: https://github.com/monkey30440/mobile_base/issues/20; parent map: https://github.com/monkey30440/mobile_base/issues/18. Scope authority is the new map/user requirements only. This note contains evidence and candidates, not an architecture selection. No existing project implementation, old map or existing spec was consulted. Environment date: 2026-10-02. Retrieved upstream manifests are the release baseline actually observable, not an invented future release.

## Mapping: save once, reuse for localization/navigation

Requirement → capability → responsibility: Teleop mapping must produce a persistent, reloadable spatial representation; operator motion remains the base/Teleop responsibility; SLAM owns estimating the map and `map→odom`; persistence owns saving/loading the representation.

**CONFIRMED native capability:** slam_toolbox supports synchronous/asynchronous 2D mapping. Its pinned [README](https://github.com/SteveMacenski/slam_toolbox/blob/2.8.5/README.md) distinguishes occupancy map saving for AMCL from pose-graph serialization for continued mapping or slam_toolbox localization. Pinned [map saver source](https://github.com/SteveMacenski/slam_toolbox/blob/2.8.5/src/map_saver.cpp) invokes `nav2_map_server map_saver_cli`; [common implementation](https://github.com/SteveMacenski/slam_toolbox/blob/2.8.5/src/slam_toolbox_common.cpp) exposes serialization/deserialization services. Native Nav2 [map server](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_map_server/src/map_server/map_server.cpp) and [map IO](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_map_server/src/map_io.cpp) load saved occupancy metadata/image for navigation costmaps and AMCL.

Completeness: the software workflow has a native save/reload route. No confirmed need for a custom mapping algorithm or custom map persistence runtime. Candidate A: slam_toolbox mapping → occupancy image/YAML → map_server + AMCL. Candidate B: additionally serialize pose graph → slam_toolbox localization. These are alternatives, not a decision to maintain both formats or both localizers. One active owner of `map→odom` is necessary; concurrent mapping/localizer ownership is not a solution.

**REQUIRES HARDWARE VALIDATION:** map quality, repeated save/reload usability and successful positioning/navigation using the actual lidar, odometry and AMR motion. **REQUIRES CALIBRATION:** sensor extrinsics, wheel/odometry scale and appropriate map resolution based on measured performance. File existence alone is not evidence of useful map quality.

## Localization: active startup without an established map pose

Requirement → capability → responsibility: support unlocalized startup (including physically outside the mapped region), allow operator Teleop into map, then accept Initial Pose and estimate robot pose for navigation. Bringup readiness and localization establishment must remain separate.

**CONFIRMED:** AMCL's pinned [implementation](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_amcl/src/amcl_node.cpp) declares `set_initial_pose` false; accepts `initialpose`/SetInitialPose; gates pose publication and `map→odom` broadcast on `initial_pose_is_known_`. `always_reset_initial_pose` permits requiring a new initial pose on reset. Thus AMCL can be lifecycle active while intentionally lacking a map pose; it need not first successfully locate the robot outside the map. This proves the component behavior, not readiness of every other Nav2 component before map TF exists. Base-frame/odom Teleop must not depend on map localization. The [NavigateToPose navigator](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_bt_navigator/src/navigators/navigate_to_pose.cpp) requires transforms to initialize a navigation goal, providing native failure behavior when pose transforms are unavailable.

**CONFIRMED alternative primitive:** slam_toolbox [localization implementation](https://github.com/SteveMacenski/slam_toolbox/blob/2.8.5/src/slam_toolbox_localization.cpp) loads a serialized pose graph and subscribes to `initialpose`; it is not simply AMCL with a renamed input map. Its pose-graph load/relocalize lifecycle must be evaluated separately if selected. AMCL evidence alone is insufficient to claim identical delayed-initialization behavior for this alternative.

**UNRESOLVED architecture/product semantics:** `initial_pose_is_known_` records initialization, not independently proven localization accuracy or convergence. A fresh TF or covariance is evidence of an estimate, not a guarantee of correct physical localization. Decide what observable evidence makes localization usable, and who prevents autonomous requests before that state. Do not invent a health FSM or global-relocalization requirement; none was requested. A native operator workflow/BT gate may suffice; custom runtime is justified only if the chosen native integration cannot meet the decided responsibility.

**REQUIRES HARDWARE VALIDATION:** startup physically outside the map, Teleop entry without autonomous command, initial pose acceptance and usable localization under actual scan/odometry ambiguity. **REQUIRES CALIBRATION:** practical covariance, scan model and positioning tolerances. Bringup lifecycle dependencies/timeouts while `map→odom` is absent belong to the Bringup decision, not a conclusion that all servers must already be active.

## Navigation: what native primitives do and do not guarantee

Requirement → capability → responsibility: expose NavigateToPose(x,y,yaw); connect current pose onto a manually prepared route graph; normally traverse the graph; leave near the target to reach its complete pose; permit obstacle-driven local deviation followed by return; fail rather than silently bypass this policy.

**CONFIRMED baseline distinction:** default [NavigateToPose BT](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_bt_navigator/behavior_trees/navigate_to_pose_w_replanning_and_recovery.xml) periodically computes a costmap freespace path then follows it. Native NavFn/Smac/Theta* freespace planning alone does not encode a mandatory route graph. Waypoint requests similarly do not establish compliance between points. Cost penalties/preferences are not proof of a mandatory normal-route policy.

**CONFIRMED graph primitives in stable Jazzy:** [ComputeRoute action](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_msgs/action/ComputeRoute.action) accepts pose or node-ID start/goal, returns a graph route and dense path, with no-valid-graph/no-valid-route/TF/timeout errors. [ComputeAndTrackRoute](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_msgs/action/ComputeAndTrackRoute.action) adds progress feedback and rerouting information, not motor control. [goal intent extraction](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_route/src/goal_intent_extractor.cpp) chooses nearby graph nodes, optionally considering costmap reachability, and prunes endpoint edges. [path conversion](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_route/src/path_converter.cpp) interpolates graph geometry, optionally smooths corners, and assigns final orientation from the last graph edge. It does not append a freespace connector to the exact requested off-graph x/y/yaw. Route tracking completion uses generous node-radius/progress semantics in [tracker source](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_route/src/route_tracker.cpp); it is not final-pose goal achievement.

**CONFIRMED native composition primitives:** pinned [BT CMake registration](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_behavior_tree/CMakeLists.txt) builds ComputeRoute, ComputeAndTrackRoute, cancel, ConcatenatePaths, GetCurrentPose, GetPoseFromPath and ArePosesNear plugins. [navigator plugin loading](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_bt_navigator/src/bt_navigator.cpp) loads built-in libraries, and [NavigateToPose action](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_msgs/action/NavigateToPose.action) permits a BT file. Upstream tests exist for [route BT action](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_behavior_tree/test/plugins/action/test_compute_route_action.cpp), [path concatenation](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_behavior_tree/test/plugins/action/test_concatenate_paths_action.cpp), [route server](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_route/test/test_route_server.cpp) and [intent search](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_route/test/test_goal_intent_search.cpp). They establish individual responsibilities; their existence is not a passed full V1 scenario.

Candidate native integration: a project-owned BT/configuration can compose route computation, freespace endpoint connectors and FollowPath while retaining the native NavigateToPose endpoint. This is a candidate to validate before writing any C++ orchestration. The modern documented tree must not be copied unexamined: optional connector branches must succeed when omitted; final yaw must remain the requested yaw even if endpoint positions coincide; unsupported newer node names must be checked against 1.3.13; path smoothing must not erase route policy. No complete stable-Jazzy shipped BT was found that proves all V1 requirements end-to-end.

**CONFIRMED final-pose primitive:** [SimpleGoalChecker](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_controller/plugins/simple_goal_checker.cpp) checks xy and yaw tolerances. Final target accuracy is tolerance-based, not exact floating-point equality. Goal checker must see the actual target pose, not only route-end edge heading. Selecting controller/goal checker/tolerances remains a decision.

**CONFIRMED avoidance primitive, bounded claim:** [MPPI PathAlignCritic](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_mppi_controller/src/critics/path_align_critic.cpp) can suppress path-alignment cost when local path occupancy is high, allowing obstacle avoidance. It otherwise penalizes path departure; this is an optimization preference, not a strict return-to-graph postcondition. Other native controllers are candidates according to kinematics and obstacle behavior; MPPI is not selected by this note. [route collision operation](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_route/src/plugins/route_operations/collision_monitor.cpp) detects blocked graph edges and requests graph rerouting or tracking failure. Graph rerouting differs from a local off-graph detour and return. Enabling edge invalidation may prevent precisely the local deviation the requirement permits; policy must be chosen intentionally.

## Completeness, gaps and decision frontier

| Responsibility | Native evidence | Completeness / smallest next step |
|---|---|---|
| Mapping save/reload | slam_toolbox + map_server persistence | CONFIRMED native software capability; choose persistence/localizer pairing; no confirmed custom-runtime gap |
| Delayed initial localization | AMCL activation vs initial-pose gating | CONFIRMED component capability; whole bringup sequencing and usability semantics require decision/integration evidence |
| Mandatory normal graph route | Route Server graph search/path | Native graph computation is CONFIRMED; direct default NavigateToPose is incomplete |
| Off-graph start/end and target yaw | Planner, route BT primitives, goal checker | Confirmed graph-only gap; minimal candidate is native BT/configuration composition; complete Jazzy-compatible integration remains UNRESOLVED |
| Necessary obstacle deviation and return | Controller path costs; route progress/errors | Physical success requires validation; strict policy enforcement/observable compliance is UNRESOLVED, not proven by soft critics |
| Failure when route-compliant navigation cannot finish | Native action errors, controller progress, finite BT recovery | Native failure primitives CONFIRMED; composed tree must propagate every phase failure and avoid unrestricted freespace fallback |

The confirmed absence is an application-level end-to-end composition in the inspected stable release, not proof that custom runtime is required. Do not translate UNRESOLVED into a confirmed custom-code gap. First compare: (A) stable native primitives plus project BT/config only; (B) a small native plugin only if a precisely decided policy responsibility cannot be expressed/tested in A. No new planning algorithm, route server replacement or orchestration service is justified by current evidence.

Decision tickets should settle: map representation/localizer; localization usability and gate ownership; interpretation of “along route”, “near target”, “necessary local deviation” and “return” sufficient to assess native completeness; route and connector composition plus failure ownership; controller choice based on proven kinematics and performance. Quantitative tuning/calibration should not be fabricated to resolve missing physical evidence.

## Verification boundary and handoff

Source inspection only; upstream tests were read/located, not executed. No runtime modification and no invented test infrastructure. Later use the repository-approved Docker workflow for Jazzy plugin loading/action/BT integration tests, including: absent initial pose; off-graph start; off-graph goal; coincident route end with different target yaw; no connector required; blocked edge with viable local deviation; inability to return; no route; unreachable final connector; bounded failure; cancel before Teleop. A simulator/software test validates integration behavior, not actual AMR localization or obstacle performance. Actual route adherence, return after detour, goal tolerance and cancel/stop behavior require hardware observation. This research ticket can close with bounded findings; the map cannot be declared cleared until human architecture decisions address the frontier.

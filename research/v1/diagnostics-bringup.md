## Requirement → responsibility → evidence → completeness

### Diagnostics: understandable current component faults

**CONFIRMED — native representation and aggregation.** DiagnosticStatus supplies severity OK/WARN/ERROR/STALE, component `name`, summary `message`, `hardware_id`, and key/value context. This directly represents the requested component/source, basic state/cause, and troubleshooting data, provided the producer actually supplies them. It does not discover faults or prescribe checks. [DiagnosticStatus 5.3.8](https://github.com/ros2/common_interfaces/blob/5.3.8/diagnostic_msgs/msg/DiagnosticStatus.msg).

**CONFIRMED — native producer tools.** `diagnostic_updater` registers diagnostic tasks, hardware identifiers and periodic publication; frequency/timestamp helpers measure publication behavior. Responsibility stays with the task author / component producer: an updater without the appropriate checks cannot identify USB disconnects, drive fault registers, invalid IMU samples or stalled sensor streams. Frequency/timestamp tools are building blocks, not a standalone monitor automatically subscribing to every robot topic. [Updater 4.2.7](https://github.com/ros/diagnostics/blob/4.2.7/diagnostic_updater/include/diagnostic_updater/diagnostic_updater.hpp), [publisher helpers](https://github.com/ros/diagnostics/blob/4.2.7/diagnostic_updater/include/diagnostic_updater/publisher.hpp), [released updater tests](https://github.com/ros/diagnostics/blob/4.2.7/diagnostic_updater/test/diagnostic_updater_test.cpp).

**CONFIRMED — absent/stale diagnostic detection is already native.** GenericAnalyzer's `expected` names identify missing entries, including names never received; missing names are represented in output and can elevate the group to ERROR or STALE. GenericAnalyzerBase applies `timeout` to last diagnostic arrival and marks stale items; `discard_stale` changes visibility. Thus an expected-item manifest and timeout configuration can cover absent/stale **diagnostic producers**, without inventing a custom watchdog for this responsibility. This is not equivalent to sensor sample freshness: a healthy-looking diagnostic heartbeat can continue while sensor data stops unless its producer measures the stream. [GenericAnalyzer](https://github.com/ros/diagnostics/blob/4.2.7/diagnostic_aggregator/src/generic_analyzer.cpp), [GenericAnalyzerBase](https://github.com/ros/diagnostics/blob/4.2.7/diagnostic_aggregator/include/diagnostic_aggregator/generic_analyzer_base.hpp), [expected/stale fixture](https://github.com/ros/diagnostics/blob/4.2.7/diagnostic_aggregator/test/expected_stale_analyzers.yaml), [discard behavior tests](https://github.com/ros/diagnostics/blob/4.2.7/diagnostic_aggregator/test/test_discard_behavior.py). Test inspection is evidence of upstream intent, not a local test run.

**CONFIRMED — operator presentation exists.** Upstream diagnostics documents `rqt_robot_monitor` for aggregated status and `rqt_runtime_monitor` for unaggregated status. These are candidate native current-status displays; no V1 requirement establishes a remote historical service, database or fleet dashboard. [Diagnostics 4.2.7 README](https://github.com/ros/diagnostics/blob/4.2.7/README.md).

**CONFIRMED — component lifecycle / runtime status is partly supplied natively.** Nav2 lifecycle manager emits diagnostics for its managed lifecycle group (ACTIVE, INACTIVE and UNCONFIGURED are OK; transition UNKNOWN is ERROR; finalized WARN). `is_active` only reports the manager's ACTIVE state; neither it nor an OK diagnostic proves scan quality, localization correctness, physical drive response or whole-system readiness. [Manager diagnostic callback and isActive](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_lifecycle_manager/src/lifecycle_manager.cpp#L150-L198). Its source names critical missing heartbeat servers in logs and resets related managed nodes on broken bonds, but this does not monitor arbitrary non-bonded hardware drivers or the entire host. [Bond handling](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_lifecycle_manager/src/lifecycle_manager.cpp#L475-L508).

**CONFIRMED — ros2_control, if chosen in the drive decision, supplies controller/hardware lifecycle and runtime-loop diagnostics.** Controller manager registers Controllers Activity, Hardware Components and Controller Manager diagnostic callbacks and publishes state-change activity. Read/write ERROR stops controllers using that hardware; controller update ERROR deactivates the controller/chain. These mechanisms depend on the hardware plugin returning meaningful errors; they do not decode an M1 Modbus fault or guarantee a physical stop. [Released controller manager source](https://github.com/ros-controls/ros2_control/blob/4.48.1/controller_manager/src/controller_manager.cpp), [released user documentation](https://github.com/ros-controls/ros2_control/blob/4.48.1/controller_manager/doc/userdoc.rst). This is a candidate, not a decision to adopt ros2_control.

**CONFIRMED — estimator diagnostics, if robot_localization is chosen, cover some configuration/data abnormalities.** `print_diagnostics` enables filter diagnostic tasks; source reports issues such as insufficient measured state/velocity, configuration conflicts and bad covariance/transform input, and sets up filtered-odometry publication-frequency diagnostics. It is not a map-localization established/lost authority or proof that every required source is fresh. [robot_localization 3.8.3 RosFilter](https://github.com/cra-ros-pkg/robot_localization/blob/3.8.3/src/ros_filter.cpp).

**CONFIRMED — host monitoring primitives exist.** Released diagnostic_common_diagnostics includes Linux CPU, RAM, disk, NTP and sensors monitors; CPU/RAM use psutil. NVIDIA tegrastats independently exposes Jetson resource, temperature and power information for troubleshooting. Generic Linux monitors' coverage of AGX Orin thermal/throttling fields and permissions must be checked on the selected image; tegrastats output alone is not a ROS diagnostic producer. [CPU monitor](https://github.com/ros/diagnostics/blob/4.2.7/diagnostic_common_diagnostics/diagnostic_common_diagnostics/cpu_monitor.py), [RAM monitor](https://github.com/ros/diagnostics/blob/4.2.7/diagnostic_common_diagnostics/diagnostic_common_diagnostics/ram_monitor.py), [monitor package](https://github.com/ros/diagnostics/tree/4.2.7/diagnostic_common_diagnostics), [NVIDIA tegrastats](https://docs.nvidia.com/jetson/archives/r34.1/DeveloperGuide/text/AT/JetsonLinuxDevelopmentTools/TegrastatsUtility.html). Archived NVIDIA evidence establishes the utility's capability, not a selected V1 JetPack version.

**UNRESOLVED — actual V1 coverage completeness.** Full coverage cannot be claimed until selected M1 / IIM-42652 / picoScan150 driver versions and their diagnostics/status outputs are assessed against failures important to Mapping, Localization and Navigation. Hardware/driver evidence belongs to [research #19](https://github.com/monkey30440/mobile_base/issues/19). Inventory needed for the decision: connection/transport failures, device-reported fault/status, sample invalidity/freshness, wheel feedback/odometry, relevant TF availability, map loading/saving failure, lifecycle transition failure, navigation action errors and host resource exhaustion. This is a responsibility inventory derived from workflows, not a new subsystem design.

**Confirmed boundary / minimal supplement candidates:** diagnostic transport and aggregation cannot create unreported device causes. First use driver/native status and existing updater tasks, then aggregator configuration for expected/stale diagnostic entries. Only where selected-source evidence confirms a missing requirement-specific check should a small component-owned check or observer be considered. Ownership nearest to evidence is a candidate: driver for protocol/device faults; producer for its output validity; lifecycle manager for managed state/bonds; aggregator for naming/grouping/expected diagnostic presence. A separate broad health manager, replicated fault state machine or historical backend has no confirmed justification here.

### Bringup: scenario usability separate from localization

**CONFIRMED — native execution and lifecycle mechanisms.** Launch starts processes and supports process events; composition loads components. Managed lifecycle gives configure/activate/deactivate/cleanup transitions, whose actual success means whatever that node implements. ProcessStarted and component load success are therefore insufficient evidence of workflow usability. [Jazzy ProcessStarted](https://docs.ros.org/en/jazzy/p/launch/_modules/launch/events/process/process_started.html), [ROS lifecycle design](https://design.ros2.org/articles/node_lifecycle.html), [Jazzy composition](https://docs.ros.org/en/jazzy/p/composition/index.html).

**CONFIRMED — native split localization/navigation startup.** Nav2 1.3.13 ships separate localization launch and navigation launch files, with distinct managers and `autostart` configuration. Localization manager handles map_server/amcl. Non-composed launch respawn is available, while that argument explicitly does not apply to composed nodes. Nav2 bringup is navigation/localization infrastructure, not complete drive/IMU/LiDAR/Teleop deployment for this robot. [Localization launch](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_bringup/launch/localization_launch.py), [Navigation launch](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_bringup/launch/navigation_launch.py).

**CONFIRMED — AMCL ACTIVE without Initial Pose is native.** With no configured initial pose, AMCL can activate, establish its bond and accept a later Initial Pose; it suppresses pose publication and map→odom updates until initial pose is known. This allows localization infrastructure to exist while localization is not established. Initial pose received is not proof of converged/correct localization. [AMCL on_activate](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_amcl/src/amcl_node.cpp#L269-L312), [pose publication guard](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_amcl/src/amcl_node.cpp#L948-L966), [TF guard](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_amcl/src/amcl_node.cpp#L1036-L1047).

**CONFIRMED — stock all-ACTIVE navigation startup has a localization dependency.** Costmap activation waits for global_frame→robot_base_frame TF and returns FAILURE after `initial_transform_timeout` (default 60 seconds). The released default global costmap uses `map`; the planner activates that costmap and propagates failed activation. Without AMCL map→odom or another legitimate global pose source, native all-active navigation autostart can time out. Setting an invented identity map→odom would not establish localization and is not a justified solution. [Costmap activation](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_costmap_2d/src/costmap_2d_ros.cpp#L275-L315), [default frames](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_bringup/params/nav2_params.yaml), [planner activation](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_planner/src/planner_server.cpp#L182-L201).

**Native supplement candidate, not decision:** lifecycle manager exposes CONFIGURE (leaves nodes INACTIVE) and RESUME (activates), besides STARTUP; separate managers and `autostart=false` permit a staged native startup boundary. This could support a product meaning of Navigation Bringup complete = base/sensors/Teleop and localization input ready, navigation servers prepared but activation/use pending localization. Operator-triggered native activation after localization might avoid project runtime orchestration if accepted. Exact readiness acceptance, operator action, activation owner and what constitutes established localization remain decision #27. A fully automatic handoff would require evaluating a real gap first. [Manager service commands](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_lifecycle_manager/src/lifecycle_manager.cpp#L118-L146), [configure / resume](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_lifecycle_manager/src/lifecycle_manager.cpp#L329-L342), [resume implementation](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_lifecycle_manager/src/lifecycle_manager.cpp#L400-L424).

**UNRESOLVED — complete scenario composition / acceptance.** Mapping needs base/odometry/TF, scan, Teleop, selected SLAM and save capability; Navigation additionally needs selected map/localization/navigation capabilities. Research #19/#20/#22 determines those choices. No generic upstream launch can know this robot's complete required set without project configuration. Minimal scenario launch/configuration composition is a candidate; this alone does not justify a new runtime readiness manager. The product explicitly permits Navigation Bringup complete with localization not established, so missing map pose in that legal state must not automatically mean bringup fault. Genuine sensor/base faults remain faults.

### Cancel navigation → Teleop boundary

**CONFIRMED — native controller cancellation has termination and zero-command behavior.** In released ControllerServer, cancellation waits for the selected plugin's `cancel()` success, terminates the action, and calls `publishZeroVelocity`; zero publication depends on its setting. Requesting cancellation is thus not identical to completed cancellation. It does not acknowledge physical standstill or arbitrate a Teleop publisher. The selected BT/plugins and downstream command timeout/ownership must be assessed before asserting the whole NavigateToPose-to-Teleop handoff. [Controller cancellation](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_controller/src/controller_server.cpp#L512-L522), [zero publication](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_controller/src/controller_server.cpp#L779-L802). Command selection remains a navigation/base decision; no need to infer a new mode state machine from the operator's confirmed cancel-first workflow.

## Evidence classes and followups

- **CONFIRMED:** released source/API capabilities and boundaries above; expected/stale native diagnostics; separate lifecycle managers; AMCL active/uninitialized state; global costmap activation TF requirement. Static primary-source inspection only.
- **UNRESOLVED:** selected driver coverage; exact meaningful monitored set and thresholds; whole-scenario readiness definition/owner; localization establishment criterion; native staged activation operator workflow; selected BT cancellation chain and command-source arrangement. These feed decisions and other research, not a reason to declare hardware-backed facts.
- **REQUIRES HARDWARE VALIDATION:** actual USB/RS485/IMU/Ethernet disconnect/reconnect and device fault propagation; data stall vs diagnostic heartbeat; host monitors and permissions on selected Jetson image; scenario startup outside map with Teleop usable; Initial Pose then global TF/costmap activation; driver/controller fault effect and measured stopping behavior; cancellation-to-Teleop handoff; sustained resource load and thermal behavior.
- **REQUIRES CALIBRATION:** acceptable measured sensor/update freshness windows where not protocol-defined, relevant frame/extrinsic/odometry/IMU calibration and localization accuracy/convergence criteria. CPU/memory warning levels are operating-policy tuning, not geometric calibration. Values are not invented in this research.

No runtime code was modified, no software build/test or hardware validation was run, and no existing evidence was claimed. Source inspection answered native API/implementation boundaries without inventing parallel validation infrastructure. Subsequent software verification should use the approved repository container workflow once the chosen composition/configuration exists; source/test reading does not increase evidence strength to runtime or hardware proof.

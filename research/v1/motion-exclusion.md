# V1 Navigation / Teleop mutual-exclusion research

Authority: [research #28](https://github.com/monkey30440/mobile_base/issues/28), [map #18](https://github.com/monkey30440/mobile_base/issues/18), and [current platform decision #22](https://github.com/monkey30440/mobile_base/issues/22). User initially requested complete mutual exclusion, then explicitly clarified its V1 boundary: **mutual exclusion is an Operator procedure, not system enforcement**. End Teleop before Navigation; cancel Navigation and wait for terminal completion before Teleop. Zero velocity or command timeout does not mean a session ended. Automated admission/refusal/switching and a custom mode manager are not required. V1 retains `NavigateToPose`; ros2_control + diff_drive_controller have been selected. twist_mux was not adopted. No existing specs, old maps or project-owned implementation were inspected.

This note researches evidence and candidate responsibility boundaries only. It records the latest user-approved operator boundary as decision input, does not invent a Teleop task/API or select a manager/wrapper, and does not define downstream Navigation/Bringup design. System-enforced exclusion is outside current V1 scope.

## Responsibilities that must not be conflated

| Required question | What must be demonstrated |
| --- | --- |
| Command selection | Exactly the authorized velocity source reaches the selected base controller. |
| Operation exclusion | Navigation cannot begin while Teleop is operating, and Teleop cannot begin while Navigation is operating. An idle/zero command does not inherently mean an operation has ended. |
| Handoff completion | Ending/canceling one operation completes before the other can start; in-flight or new requests cannot race through another entrypoint. |
| Software stop | Previous commands cannot continue/reappear through queues, retained reference, downstream processing or old action execution. |
| Physical stop | Actual wheel/base motion meets the chosen stopping criterion; this needs hardware evidence. |

The second and third rows describe the initially researched stronger enforcement boundary. The final user clarification makes them Operator responsibilities in current V1, not automatic system obligations: stop/end Teleop before starting Navigation; cancel Navigation and wait for its terminal completion before starting Teleop. A zero command or timeout alone does not end the operation. No requirement was confirmed for automatic physical-standstill admission checking.

## Native capabilities and strict limits

### Native NavigateToPose action admission and lifecycle

**CONFIRMED.** Nav2 SimpleActionServer `handle_goal()` rejects all incoming goals while inactive; while active it accepts and executes. `handle_cancel()` accepts a cancellation request for an active handle, not a promise that execution has ended. Activation/deactivation are therefore genuine server-side primitives that apply to ordinary `NavigateToPose` clients, including clients outside an operator script. Deactivation first disables new acceptance and requests existing execution to stop, then waits; source also handles stop deadlines and still-running callbacks. It is not a shared Teleop/Navigation ownership protocol. [SimpleActionServer 1.3.13](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_util/include/nav2_util/simple_action_server.hpp), [released tests: activation, inactive rejection, cancellation, preemption](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_util/test/test_actions.cpp).

**CONFIRMED.** NavigateToPoseNavigator's `goalReceived()` loads the requested/default BT and initializes the goal. The BehaviorTreeNavigator base has NavigatorMuxer, allowing one navigator plugin to operate at a time. Its scope is registered navigator plugins, not ordinary Teleop publishers or a general mobile-base operation lock. The goalReceived callback runs inside execution **after action acceptance**; returning false terminates an already accepted goal rather than rejecting the original goal request. These are useful native extension hooks, but a shared cross-operation predicate would be project runtime behavior, not YAML-only native functionality. [NavigateToPoseNavigator](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_bt_navigator/src/navigators/navigate_to_pose.cpp), [NavigatorMuxer / BehaviorTreeNavigator](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_core/include/nav2_core/behavior_tree_navigator.hpp), [BtActionServer execution callback](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_behavior_tree/include/nav2_behavior_tree/bt_action_server_impl.hpp#L295-L354).

**CONFIRMED.** Native BT configuration can sequence known actions and cancellation nodes. Inspected released condition nodes do not include a general Teleop-active mutual-exclusion condition. More fundamentally, a BT that serializes one caller's requests cannot prohibit a separate raw NavigateToPose client from invoking its server, nor prohibit a standalone Teleop publisher. NavigateToPose goal's `behavior_tree` field permits a requested alternative tree; a policy enforced only in a default tree needs a separate guarantee covering every permitted tree. No complete bilateral operation lock was identified in the inspected native BT components. [Released condition directory](https://github.com/ros-navigation/navigation2/tree/1.3.13/nav2_behavior_tree/plugins/condition), [goalReceived and preemption handling](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_bt_navigator/src/navigators/navigate_to_pose.cpp#L99-L114), [native BT plugin list](https://docs.nav2.org/jazzy/configuration_and_development/navigation_plugins/).

### Ordinary Teleop versus native AssistedTeleop

**CONFIRMED.** Released teleop_twist_keyboard creates an ordinary rclpy node/publisher and sends velocity, with a final zero command on exit. teleop_twist_joy is an ordinary rclcpp Node; its enable button permits joystick output and releases to zero. Neither exposes a ROS lifecycle or bilateral Navigation admission protocol in the inspected implementation. Process existence, enable-button release, absence of packets and a zero Twist do not define a shared operation session that Nav2 automatically owns or knows. [keyboard 2.4.1](https://github.com/ros2/teleop_twist_keyboard/blob/2.4.1/teleop_twist_keyboard.py), [joystick 2.6.5](https://github.com/ros2/teleop_twist_joy/blob/2.6.5/src/teleop_twist_joy.cpp).

**CONFIRMED — important native alternative, still incomplete for exclusion.** Nav2 supplies AssistedTeleop as a cancellable behavior action. It consumes `cmd_vel_teleop`, applies its behavior processing, supports duration/preempt completion, and produces commands through the behavior's publisher. This offers native action/session machinery if its functionality is appropriate, but it is not the standard keyboard/joy tool's own lifecycle. TimedBehavior instantiates its own SimpleActionServer and has no shared NavigatorMuxer with NavigateToPose. Thus AssistedTeleop and NavigateToPose do not gain cross-mode exclusion simply by launching both. Its costmap/TF dependencies and assisted behavior must also be evaluated before using it for the required unlocalized Teleop workflow; this research does not adopt it. [AssistedTeleop implementation](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_behaviors/plugins/assisted_teleop.cpp), [TimedBehavior action/cancel/stop machinery](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_behaviors/include/nav2_behaviors/timed_behavior.hpp), [native CancelAssistedTeleop](https://docs.nav2.org/configuration/packages/bt-plugins/actions/CancelAssistedTeleop.html).

### twist_mux command priority and locks

**CONFIRMED.** twist_mux selects a velocity input using priority, freshness and lock priority. A Bool lock suppresses lower-priority inputs; lock timeout can remain locked when expired. It forwards the selected source's incoming commands. The implementation neither cancels NavigateToPose nor rejects action goals or ends keyboard/joystick operation. Lock signal production and synchronization would belong to another owner; configuring priorities/locks cannot itself supply the missing bilateral admission protocol. This explains why command arbitration does not meet the newly confirmed operation requirement. It is evidence about limits, not a recommendation to adopt rejected twist_mux. [twist_mux 4.5.0](https://github.com/ros-teleop/twist_mux/blob/4.5.0/src/twist_mux.cpp), [velocity and lock handles](https://github.com/ros-teleop/twist_mux/blob/4.5.0/include/twist_mux/topic_handle.hpp).

### ros2_control resource ownership / switching

**CONFIRMED.** Controller-manager switching deactivates/activates specified controllers in its control loop; STRICT fails on switch errors, and released AUTO/FORCE_AUTO variants can resolve conflicting controller interfaces. Native exclusive command-interface claims protect hardware resources between controllers. This is controller ownership, not operator/task admission. A single active diff_drive_controller receiving commands from two publishers sees a command stream, not two separately claimed controllers or tasks. Switching two controllers with the same wheel interfaces could separate actuator ownership, but it does not cancel/reject Navigation goals or terminate Teleop, and would require a coordinating operation owner. It cannot by itself prove the user requirement. [SwitchController 4.48.1](https://github.com/ros-controls/ros2_control/blob/4.48.1/controller_manager_msgs/srv/SwitchController.srv), [controller-manager tests, including claimed-interface activation failures](https://github.com/ros-controls/ros2_control/blob/4.48.1/controller_manager/test/test_controller_manager.cpp).

**CONFIRMED.** diff_drive_controller consumes TwistStamped when active, rejects inactive input, applies command timeout, and halts its wheel command interfaces on deactivation. Timeout operates on command age; it is not an explicit Teleop end or NavigateToPose terminal status. Deactivation/halt and zero velocity are software commands, not measured physical stopping evidence. [diff_drive_controller 4.42.1](https://github.com/ros-controls/ros2_controllers/blob/4.42.1/diff_drive_controller/src/diff_drive_controller.cpp).

## Cancellation, terminal result and stop evidence

**CONFIRMED.** ROS action cancellation response identifies goals transitioning to CANCELING; terminal CANCELED comes later through status/result. ACCEPTED, EXECUTING and CANCELING are nonterminal. Merely receiving a successful cancel service response cannot release exclusive ownership safely if the old operation still executes. [ROS action state and cancellation semantics](https://design.ros2.org/articles/actions.html), [CancelGoal interface](https://github.com/ros2/rcl_interfaces/blob/jazzy/action_msgs/srv/CancelGoal.srv).

**CONFIRMED.** Nav2 BT cancellation halts child actions; BtActionNode halt waits for cancel response and result with timeouts and can log timeout failures. BtActionServer halts the tree before reporting its own final status. ControllerServer waits for plugin `cancel()` success, terminates its action and requests zero publication according to configuration. Therefore parent NavigateToPose terminal state is useful evidence, but does not establish that every failed/timed-out downstream cancellation has stopped, that downstream buffers cannot retain command, or that the AMR is physically stationary. The actual selected chain must be verified. [BT child halt](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_behavior_tree/include/nav2_behavior_tree/bt_action_node.hpp#L313-L342), [BT server finalization](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_behavior_tree/include/nav2_behavior_tree/bt_action_server_impl.hpp#L324-L354), [ControllerServer cancellation / zero command](https://github.com/ros-navigation/navigation2/blob/1.3.13/nav2_controller/src/controller_server.cpp#L512-L522).

## Completeness result under final operator-procedure scope

**CONFIRMED — native primitives support the user-approved procedural boundary.** Native action cancel plus final result/status supports “cancel Navigation, wait terminal completion, then Teleop.” Ordinary keyboard Teleop can be explicitly ended by process exit, whose implementation attempts a final zero command; joystick/button semantics need to remain explicit in the selected tool's operator procedure. Neither an idle/zero command nor base timeout constitutes the operator ending Teleop. diff_drive_controller timeout/deactivation supplies the already selected base's command handling, independently of operator session semantics.

No project-owned automated admission/reject/switch runtime responsibility is justified by the final requirement. The platform decision may record the approved operator procedure, supported Teleop termination operation and native cancellation/result boundary. This note supplies evidence; decision #22 remains the owner of the user's architecture approval.

**OUT OF SCOPE — stronger system-enforced exclusion.** The inspected native combination does not share bilateral automatic Navigation/Teleop admission ownership. An operator script is bypassable by independent standard NavigateToPose clients; command priority, locks and controller switching do not cancel/end both operation types. These are facts about a stronger hypothetical requirement, **not a confirmed V1 gap** after the user's clarification. Do not create custom mode-manager, action-wrapper, Teleop session API, queue or conflict policy work from this research.

## Evidence classes / validation followups

- **CONFIRMED:** source/API boundaries above; active/inactive raw goal admission, navigator-only mux scope, ordinary Teleop publisher model, AssistedTeleop's separate server, command-only mux locks, controller resource ownership and cancel/nonterminal semantics.
- **CONFIRMED PRODUCT BOUNDARY:** operator-procedure exclusion; stop/end Teleop before Navigation; cancel Navigation and await terminal completion before Teleop; zero velocity/timeout does not end a session; no automatic admission/refusal/switch or custom mode manager requirement.
- **UNRESOLVED:** exact chosen Teleop tool and its explicit operator end operation; selected downstream cancellation/stop behavior. System-enforced admission and raw-client exclusion are outside current V1, not unresolved blockers.
- **REQUIRES HARDWARE VALIDATION:** cancellation/timeout/deactivation actual M1 response; wheel/base stopping time and distance; USB/RS485 failure during handoff; stale commands after reconnect; observed bilateral switching. Software proof of admission/command exclusivity cannot substitute for physical-stop evidence.
- **REQUIRES CALIBRATION:** any chosen physical standstill threshold, measurement tolerance or measured stopping bound needs relevant sensing/measurement justification. No values are invented here.

Future relevant software verification should cover the selected operator workflow: native cancel pending versus terminal completion, explicit Teleop end versus silence, timeout/retained command and failure/restart behavior, using the repository's existing container mechanisms when an approved composition exists. Automatic concurrent-request/bypass enforcement tests are outside the confirmed V1 boundary. No runtime changes or local test executions occurred in this research; no physical evidence is claimed.

# V1 LiDAR scan-frame preflight

Research date: 2026-10-07. Scope: #37/#38 picoScan150 native scan coordinates and model child frames. No device access, runtime edits, or calibration performed. Source code is pinned to `sick_scan_xd` **3.9.0**.

## Confirmed native conventions

- The official supplied manual defines a single device-coordinate origin for all beams and distance measurements. Zero azimuth is the main viewing direction, normal to the front side; positive angular direction is counterclockwise. The picoScan has one scan plane, ideally at elevation zero. Data remains in device coordinates. See [supplied SICK operating instructions](../../reference/operating_instructions_picoscan150_2d_lidar_sensors_en_im0106691.pdf), document `8028323/1XQ7/2026-09-17`, sections 3.5.5 (printed pp. 20–21) and 3.5.6.5.2 (printed p. 24).
- Native `LaserScan` construction splits points by echo and layer, copies their polar range and azimuth, and computes `angle_min`/`angle_max` from the first/last ordered points. Positive `angle_increment` is their span divided by `N-1`. It does not add a transform based on the suffix. [Pinned publisher conversion](https://github.com/SICKAG/sick_scan_xd/blob/3.9.0/driver/src/sick_scansegment_xd/ros_msgpack_publisher.cpp#L681-L909).
- The frame suffix is `_<layer_idx+1>` and, when multiple echoes are published, `_<echo_idx>`. Thus observed FL `base_lidar_link_FL_1` and BR `base_lidar_link_BR_1_0`, `_1_1`, `_1_2` label one plane and its echoes. Echo numbers describe returns, not differently mounted sensors or independently rotated frames. [Pinned suffix construction](https://github.com/SICKAG/sick_scan_xd/blob/3.9.0/driver/src/sick_scansegment_xd/ros_msgpack_publisher.cpp#L860-L903). The parser assigns the same beam azimuth/elevation to each echo. [Pinned compact parser](https://github.com/SICKAG/sick_scan_xd/blob/3.9.0/driver/src/sick_scansegment_xd/compact_parser.cpp#L720-L750).
- Native picoScan launch expects fullframe coverage `-138°..+138°`, but this is a collection default, not proof of actual installed sensor filtering or exact per-message endpoints. Runtime metadata must be measured; do not hardcode an increment from those limits. [Pinned launch defaults](https://github.com/SICKAG/sick_scan_xd/blob/3.9.0/launch/sick_picoscan.launch#L17-L24).

## Transform boundary and important source nuance

The native default `add_transform_xyz_rpy` is all zeros. Launch comments describe this as a Cartesian-pointcloud transform and exclude LaserScan. However the compact parser receives `azimuthOffset()`, whose documented behavior returns yaw when a yaw-only transform is configured; that offset is added to beam azimuth before LaserScan construction. Consequently a nonzero yaw-only override cannot safely be treated as irrelevant to LaserScan solely from the launch comment. Keep the existing default and use the model TF for mounting, with no competing point-coordinate transform. [Launch comment](https://github.com/SICKAG/sick_scan_xd/blob/3.9.0/launch/sick_picoscan.launch#L65-L73), [parser offset](https://github.com/SICKAG/sick_scan_xd/blob/3.9.0/driver/src/sick_scansegment_xd/compact_parser.cpp#L699-L703), [parser invocation](https://github.com/SICKAG/sick_scan_xd/blob/3.9.0/driver/src/sick_scansegment_xd/compact_parser.cpp#L962), [transform interface](https://github.com/SICKAG/sick_scan_xd/blob/3.9.0/include/sick_scan/sick_cloud_transform.h#L130-L159).

**CONFIRMED design consequence:** the user-approved model child frames may share one optical pose for each sensor's observed layer/echo labels. Identity transforms between the BR echo aliases do not imply that the BR optical pose relative to its CAD mounting link is identity. Preserve FL LAST and BR ALL echo settings, native topics and native message frame IDs. `robot_state_publisher` owns those model transforms; the existing launcher disables native driver TF (`tf_publish_rate=0`).

## What software verification proves, and what remains

The supplied URDF's FL and BR mounting joints both have zero RPY, with distinct translations. These are CAD facts, not sufficient evidence that both device viewing directions are robot-forward. See [authoritative URDF](../../reference/FIH_AMR_ROBOT_V2.0_0731/urdf/RWF_V2.0_QA_release.urdf), `base_lidar_joint_FL` and `base_lidar_joint_BR`.

- **CONFIRMED software scope:** test TF lookup and point transformation from every observed native frame to `base_footprint`, preserve CAD translations, check unique model TF ownership and check actual received angle metadata. Passing proves wiring and numerical consistency with the declared model.
- **REQUIRES HARDWARE VALIDATION:** each sensor's optical zero direction and left/right angular sign relative to the robot. The operator can leave the robot raised and stationary: identify the sensor's front viewing direction, then place a visible target in two known positions in its visible field (one ahead of optical zero and one toward its optical left). Compare the resulting range change and transformed point location with those physical positions, one sensor at a time. Keep hands clear of moving parts; no wheel command is needed.
- **REQUIRES CALIBRATION:** actual optical-origin offset and mounting yaw/pitch/roll accuracy. A coarse obstacle observation can reject a reversed or rotated model but does not establish precise extrinsics. No arbitrary yaw, identity optical-to-CAD calibration, or measurement tolerance is confirmed by this note.

No frame rewriter, scan merger, echo-setting change, or additional runtime publisher is justified by the naming issue.

## 05 — Step 4：檢查 `Robot Description` 是否值得成為獨立 Subsystem

這一步其實是在問：

> **「描述機器人本體」這件事，是否有足夠獨立的責任，值得從其他 subsystem 裡拆出來？**

目前它主要負責的是：

```text
Robot Description
├── robot geometry
├── joint definitions
├── frame relationships
└── static robot model
```

它服務很多地方：

```text
Perception
Localization
Mapping
Navigation
Base Control
```

例如 Navigation 需要知道 footprint，Localization 需要知道 sensor frame，Base Control 需要知道 wheel joint。

所以它不是某一個 subsystem 的「內部資料」，而是整個系統共用的基礎模型。

---

### 1. 為什麼不放進 Base Control？

看起來 wheel joint 跟底盤很有關係，所以最容易想到：

```text
Base Control
└── Robot Description
```

但問題是 Robot Description 不只是描述輪子。

它還可能描述：

```text
base_link
base_footprint
lidar frames
imu frame
sensor mounting geometry
robot footprint
```

這些會直接被：

```text
Mapping
Localization
Navigation
Perception
```

使用。

如果放進 Base Control，會讓 architecture 看起來像：

> 其他 subsystem 都依賴 Base Control 才能知道機器人的幾何模型。

這個責任關係不太合理。

---

### 2. 為什麼不放進 Perception？

同樣地，LiDAR / IMU frame 跟感知很密切。

但 Robot Description 也包含：

```text
wheel joints
base frames
robot body geometry
```

所以它也不是 Perception 專屬。

---

### 3. 它比較像什麼？

它比較像一份**全系統共享的 authoritative model**：

```text
              Robot Description
              /      |       \
             /       |        \
            ▼        ▼         ▼
      Perception  Navigation  Base Control
            \        |         /
             \       |        /
              ▼      ▼       ▼
             Mapping / Localization
```

也就是：

> 其他 subsystem 使用它，但不應各自重新定義一份自己的 robot geometry / frame model。

---

### 4. 它的責任邊界應該很小

如果把它定成獨立 subsystem，我不建議讓它變得很大。

它只負責：

```text
「系統中的機器人模型是什麼」
```

不負責：

```text
TF localization estimate
wheel odometry
sensor data
motor control
navigation footprint logic
```

例如：

```text
base_link → lidar_link
```

這種固定幾何關係屬於 Robot Description。

但：

```text
map → odom
```

不是。

因為這是 runtime localization result。

同樣：

```text
odom → base_footprint
```

也不是 Robot Description 的責任。

那是 runtime motion-state ownership。

這個區分非常重要。

---

## Step 4 候選結論

我建議：

```text
S1 Robot Description
```

**保留為獨立 subsystem。**

理由很簡單：

> 它提供全系統唯一、共享的 robot geometry / joint / static frame model，而且不屬於 Perception、Navigation 或 Base Control 其中任何一方。

它主要承接：

```text

```

而它明確**不負責 runtime pose / odometry / localization TF**。

```text

LiDAR → RF2O
LiDAR → Navigation costmap
IMU   → State Estimation
```

> **被多個 subsystem 消費的共享輸入。**

```text
Sensor
  ↓
```

```text

   ↓
LaserScan

IMU driver
   ↓
sensor_msgs/Imu
```

如果雙 LiDAR 需要形成一份 merged scan，這也仍然可以視為 perception-side data preparation，因為它還是在做：

> 「把原始 sensor input 整理成後面可以共同使用的感知資料。」

但它**不負責解釋機器人在哪裡**。

---

### 4. 哪些事情明確不屬於 Perception？

這些不要塞進來：

```text
LaserScan → robot pose        ×
IMU → fused odometry          ×
LaserScan → map               ×
LaserScan → path decision     ×
```

也就是：

```text

   │
```

```text

   └── 「我怎麼動」

Localization
   └── 「我在哪裡」

Mapping
   └── 「環境長什麼樣」

Navigation
   └── 「我要怎麼走」
```

這樣責任會非常乾淨。

## 05 - Step 6：檢查 `State Estimation` 是否值得成為獨立 Subsystem

這一步其實是在問：

> **「估計機器人怎麼移動」和「估計機器人在地圖哪裡」是不是同一件事？**

答案是：**不是。**

---

### 1. 先看兩者差別

`State Estimation` 比較像：

```text
Wheel Odometry ─┐
RF2O Odometry  ─┼─→ Fusion ─→ odom → base_footprint
IMU             ─┘
```

它回答：

> **「機器人相對上一個時刻，怎麼移動？」**

而 `Localization` 是：

```text
Map
LaserScan
Odometry
   │
   ▼
AMCL
   │
   ▼
map → odom
```

它回答：

> **「機器人在這張地圖的哪裡？」**

---

### 2. 可以用兩張座標紙理解

想像機器人自己拿一張紙記錄：

```text
我往前 1 m
右轉 20°
再往前 2 m
```

這就是 odometry / State Estimation。

即使沒有地圖，它還是可以持續記錄自己的相對移動。

但是時間久了會漂移。

---

Localization 則像是機器人抬頭看環境，然後說：

```text
根據牆壁和地圖比對，
我現在應該在地圖這裡。
```

它會利用地圖去修正「我在哪裡」這件事。

所以：

```text
State Estimation
      ↓
提供連續、平滑的相對運動

Localization
      ↓
把這個運動關係對齊到 Map
```

---

### 3. 為什麼不把兩個合成一個 Subsystem？

表面看很合理：

```text
Localization / State Estimation
```

但它們有幾個很不同的 boundary。

第一個是 **Map dependency**：

```text
State Estimation
不需要 Map

Localization
需要 Map
```

這非常重要。

因為 UC-001 建圖時，我們還沒有最終 Map，但仍然需要 odometry。

也就是：

```text
Mapping Mode

Perception
    ↓
State Estimation
    ↓
Mapping
```

這時 Localization 完全可以不存在。

---

### 4. 第二個差別是 TF ownership

這裡會形成非常乾淨的責任：

```text
State Estimation
    ↓
odom → base_footprint

Localization
    ↓
map → odom
```

最後整條 TF：

```text
map
 ↓
odom
 ↓
base_footprint
 ↓
base_link
 ↓
sensors
```

可以理解成：

```text
Localization
「Map 和你的本地運動座標差多少？」

State Estimation
「在本地運動座標裡，你目前走到哪裡？」

Robot Description
「base 和各 sensor 的固定幾何關係是什麼？」
```

三個 responsibility 很自然地分開。

---

### 5. 第三個差別是 failure semantics

例如 wheel odometry 暫時失效，但 IMU / RF2O 還有效。

State Estimation 可能仍然依成熟 fusion 行為繼續產生 estimation。

這屬於：

```text
SYS-005
```

但如果 AMCL 無法使用 Map 或 LaserScan：

```text
Localization failure
```

那是另一種問題。

兩者混在一起，之後 failure ownership 會變得很難講清楚。

---

### 6. State Estimation 到底負責什麼？

我建議 responsibility 保持：

```text
Wheel state
RF2O odometry
IMU
   │
   ▼
State Estimation
   │
   ├── fused planar odometry
   └── odom → base_footprint
```

主要承接：

```text
SYS-005
```

同時依賴 Base Control 提供有效的 measured wheel feedback。

但它**不負責判斷 wheel feedback 是否可信**。

例如：

```text
Motor driver
    ↓
feedback validity
    ↓
valid wheel state
    ↓
State Estimation
```

feedback validity 的責任仍然應留在 Base Control / hardware boundary。

State Estimation 是 consumer。

---

## Step 6 候選結論

我建議：

```text
S3 State Estimation
```

**保留為獨立 subsystem。**

原因簡化成一句話：

> `State Estimation` 提供不依賴 Map 的連續相對運動估計；`Localization` 則使用 Map 將機器人的位置對齊到全域座標，因此兩者 lifecycle、dependency 與 TF ownership 都不同。

目前形成：

```text
Robot Description   → static geometry / TF
Perception          → sensor measurements
State Estimation    → odom → base_footprint
Localization        → map → odom
```

這一步其實是在問：

> **「建立地圖」和「儲存、載入、確認地圖可讀」是不是同一種責任？**

我的判斷是：

> **可以放在同一個 `Mapping` subsystem 裡，但要把內部責任分清楚。**

---

### 1. 先看兩類工作

第一類是「建圖」：

```text
LaserScan
Odometry
   │
   ▼
Mapping
   │
   ▼
Occupancy Grid
```

主要對應：

```text
SYS-001
SYS-006
```

第二類是「地圖生命週期管理」：

```text
Occupancy Grid
   │
   ├── Save
   ▼
Map Package

Map Package
   │
   ├── Read-back
   └── Load
```

主要對應：

```text
SYS-007
```

### 2. 為什麼看起來可以拆成兩個 subsystem？

因為它們做的事確實不同：

```text
Mapping
→ 建立地圖

Map Management
→ 儲存 / 載入 / 驗證地圖
```

而且 Navigation Mode 不需要建圖，卻需要載入 Map。

所以理論上可以切成：

```text
Mapping Subsystem

Map Management Subsystem
```

---

### 3. 但為什麼我不建議現在拆？

因為在目前 v0.1，Map Management 的責任量很小，而且它存在的核心目的仍然是：

> **管理 Mapping 產生並供 Localization / Navigation 使用的同一份 Map artifact。**

如果拆開，就會增加一個 architecture boundary：

```text
Mapping
   ↓
Map Management
   ↓
Localization / Navigation
```

但目前這個 boundary 並沒有帶來很明顯的獨立價值。

反而會讓 architecture 更碎。

---

### 4. 所以我建議 `Mapping` subsystem 的責任範圍是

```text
S4 Mapping
├── Create Occupancy Grid
├── Continuously update map
├── Save Map Package
├── Read-back saved map
└── Load Map Package
```

這裡的重點不是說它內部一定只有一個 ROS node。

實際成熟元件可能是：

```text
slam_toolbox
nav2_map_server
MapIO
```

但那是 implementation composition。

在 architecture 層，我們把它們視為共同服務：

> **Map lifecycle**

所以可以放在同一個 subsystem。

---

### 5. 它不負責什麼？

這點要切乾淨。

`Mapping` 不負責：

```text
「機器人在地圖哪裡」
```

那是 Localization。

也不負責：

```text
「導航應該走哪條 route」
```

那是 Navigation。

更不負責：

```text
Route Graph
Station Catalog
Navigation Configuration
```

因為這些雖然也是「場域資料」，但不是 Map 本身。

這點很重要。

不要因為它們都放在同一個 site folder，就變成：

```text
Mapping
└── 所有場域資源
```

那會把 responsibility 擴張過頭。

---

### 6. 所以 Architecture 關係可以理解成

建圖模式：

```text
Perception
    ↓
State Estimation
    ↓
Mapping
    ↓
Map Package
```

導航模式：

```text
Map Package
    ↓
Mapping
    ↓
Loaded Occupancy Grid
    ↓
Localization
    ↓
Navigation
```

也就是同一個 subsystem 同時負責 Map 的：

```text
Create
Update
Persist
Read-back
Load
```

---

## Step 7 候選結論

我建議：

```text
S4 Mapping
```

**保留為單一 subsystem，暫不再拆 `Map Management`。**

它主要承接：

```text
SYS-001
SYS-002
SYS-006
SYS-007
SYS-024
```

理由簡化成一句話：

> 建圖與 Map 儲存／載入雖然是不同操作，但目前都圍繞同一個 Map lifecycle，拆成兩個 subsystem 只會增加不必要的 architecture boundary。

## 05 — Step 9：檢查 `Navigation` 要不要維持成一個大的 Subsystem

這一步其實是在問：

> **Target Handling、Route Strategy、First/On Route/Last Mile、Planning、Tracking、Goal Completion，這些要不要放在同一個 `Navigation` subsystem？**

我的判斷是：

> **先維持成一個 Navigation subsystem，但內部要清楚分成幾個 responsibility areas。**

---

### 1. 先看整條導航責任鏈

使用者輸入：

```text
Station ID / Goal Pose
        ↓
Target Handling
        ↓
Canonical Goal Pose
        ↓
Route Strategy
        ↓
First Mile
        ↓
On Route
        ↓
Last Mile
        ↓
Goal Completion
        ↓
Navigation Result
```

同時過程中還需要：

```text
Planning
Tracking
Obstacle Avoidance
Progress Checking
Cancellation
Route Reselection
Fallback Boundary
```

這些工作的共同目的都是：

> **把一個已接受的 Navigation Target，可靠地轉成完整導航任務並執行到結束。**

---

### 2. 為什麼 Target Handling 可以放在 Navigation？

Target Handling 做的是：

```text
Station ID
   ↓
Station Resolution
   ↓
Canonical Goal Pose
```

或：

```text
x / y / yaw
   ↓
Goal Pose Normalization
   ↓
Canonical Goal Pose
```

然後再：

```text
Canonical Goal Pose
   ↓
Validation
   ↓
Navigation
```

它存在的唯一目的，就是建立一個 Navigation 可以正式接受的目標。

如果拆成：

```text
Target Subsystem
      ↓
Navigation Subsystem
```

也做得到。

但目前它的責任很小，而且：

```text
Target rejected
Target accepted
Navigation admission
```

這些 failure / lifecycle boundary 都非常接近。

因此 v0.1 沒有強烈理由多切一個 subsystem。

---

### 3. 為什麼 Route Strategy 也放在 Navigation？

我們的 Navigation 不是單純：

```text
Current Pose → Goal
```

而是：

```text
Current Pose
     ↓
找 Route Entry
     ↓
選 Route Graph route
     ↓
找 Route Exit
     ↓
Goal
```

所以 route strategy 是整個 navigation semantics 的核心。

如果把 Route Strategy 獨立出去：

```text
Route Subsystem
      ↓
Navigation Subsystem
```

就會出現很強的跨 subsystem 協調：

```text
route selection
route reselection
blocked route
first-mile feasibility
last-mile feasibility
fallback eligibility
```

這些事情其實高度耦合。

目前拆出去反而讓 boundary 更複雜。

---

### 4. First Mile / On Route / Last Mile 是三個 subsystem 嗎？

我不建議。

它們是三個 **navigation stages**：

```text
First Mile
Current → Entry

On Route
Entry → Exit

Last Mile
Exit → Goal
```

但是共同依賴：

```text
Planner
Controller
Costmap
Obstacle Avoidance
Progress Checker
Navigation state
```

如果切成三個 subsystem：

```text
First Mile Subsystem
On Route Subsystem
Last Mile Subsystem
```

會大量重複共同 navigation capabilities。

更合理的是：

```text
Navigation
├── First Mile stage
├── On Route stage
└── Last Mile stage
```

---

### 5. Planning / Tracking 為什麼也不單獨切？

因為：

```text
Planning
→ 產生 path

Tracking
→ 執行 path
```

它們雖然技術責任不同，但在 architecture 層都是 Navigation Execution 的核心成熟能力。

例如 Nav2 本身就提供：

```text
Planner Server
Controller Server
FollowPath
Costmaps
Progress Checker
Goal Checker
```

05 需要知道：

> Navigation 使用這些成熟能力完成執行。

但沒有必要因為 mature package/component 不同，就切成多個 subsystem。

---

### 6. Navigation 內部可以先保留這些責任區域

不是 06 的 component design，只是 architecture-level 分區：

```text
S6 Navigation
│
├── Target Admission
│   ├── Target discriminator
│   ├── Goal Pose normalization
│   ├── Station resolution
│   └── Canonical Goal validation
│
├── Route Strategy
│   ├── route-assisted selection
│   ├── entry / exit selection
│   └── route reselection
│
├── Stage Execution
│   ├── First Mile
│   ├── On Route
│   └── Last Mile
│
└── Navigation Supervision
    ├── obstacle handling
    ├── progress
    ├── goal completion
    ├── cancellation
    ├── fallback boundary
    └── final result
```

這樣有一個好處：

> **使用者丟進來的是 Navigation Target，從接受、執行到結果，都有單一 architecture owner。**

---

## Step 9 候選結論

我建議：

```text

```

**維持成一個 subsystem。**

它主要承接：

```text
SYS-008
SYS-009
SYS-032
SYS-033

SYS-011
SYS-013
SYS-014
SYS-015
SYS-016
SYS-017
SYS-018
SYS-019
SYS-020
SYS-021
SYS-025
```

簡單講：

> Target Handling、Route Strategy 和 Navigation Execution 雖然是不同責任，但它們共同構成一個完整 navigation task，而且共享 lifecycle、failure、reselection、cancel 與結果語意；v0.1 沒有必要在 system architecture 再把它們拆開。

## 05 - Step 10：檢查 `Base Control` 是否值得成為獨立 Subsystem

這一步其實是在問：

> **Navigation 產生的速度命令，從「命令」一路變成「輪子真的動」，以及底盤安全停止，是否應該由一個獨立 subsystem 負責？**

我的判斷是：

> **要，而且這個 subsystem 的 safety boundary 必須和 Navigation 明確分開。**

---

### 1. Base Control 的核心工作

資料流很直接：

```text
Navigation velocity command
        ↓
Command handling
        ↓
Differential-drive control
        ↓
Hardware interface
        ↓
Motor driver
        ↓
Wheels
```

反方向：

```text
Motor driver
    ↓
Measured wheel feedback
    ↓
Base Control
    ↓
State Estimation / diagnostics
```

主要承接：

```text
SYS-022
SYS-026
SYS-027
SYS-028
SYS-029
SYS-030
```

---

### 2. 為什麼不能放進 Navigation？

Navigation 負責的是：

```text
「我要怎麼走」
```

Base Control 負責：

```text
「把速度命令安全地變成底盤運動」
```

例如 Navigation 可以決定：

```text
linear.x = 0.3 m/s
angular.z = 0.2 rad/s
```

但它不應該自己處理：

```text
motor enable
driver alarm
wheel feedback validity
motor communication failure
hardware disable
```

這些都是底盤硬體邊界的責任。

所以：

```text
Navigation
    ↓
desired robot motion

Base Control
    ↓
actual safe base motion
```

---

### 3. 最重要的是：三種「停止」不是同一件事

這裡要特別分清楚。

#### A. Navigation Stop

例如：

```text
使用者 Cancel
Route 無法繼續
Navigation failure
```

Navigation 做的是：

```text
停止導航任務
    ↓
不再要求移動 / 發出零速
```

意思是：

> **「我不想再走了。」**

---

#### B. Command Timeout Stop

例如上游突然死掉：

```text
最後一次 cmd_vel
      ↓
Navigation crash / communication interruption
      ↓
沒有新的 command
```

Base Control 不能永遠保持舊命令。

所以：

```text
command timeout
      ↓
force zero motion command
```

意思是：

> **「沒人繼續叫我走，所以我必須停。」**

這主要是 SYS-027。

---

#### C. Hardware Safe Stop

這又更底層。

例如：

```text
driver alarm
communication fault
shutdown
disable request
invalid feedback
```

Base Control 必須執行：

```text
stop command
    ↓
確認 wheel stopped
    ↓
disable motor drive
```

而且某個 safety action 失敗，也不能阻止其他安全動作的嘗試。

意思是：

> **「底盤本身進入安全狀態。」**

這主要是 SYS-030。

---

### 4. 所以三層關係是

```text
Navigation
「任務應該停止」
        ↓
zero / no motion request
        ↓
Base Control
「command 是否仍有效？」
        ↓
timeout protection
        ↓
Hardware safety
「底盤是否真的安全停止？」
```

這三層不能混成一個「stop」。

否則之後很容易出現：

> Navigation 發了零速，所以就算 safe stop 完成。

這是不成立的。

零速 command 只是要求。

真正的硬體停止與確認仍然是 Base Control 的責任。

---

### 5. Base Feedback 也應該由這裡守門

馬達 driver 回傳：

```text
wheel position
wheel velocity
status
```

不能只要收到數值就當成有效 measurement。

SYS-029 要求的是：

```text
Motor feedback
      ↓
validity check
      ↓
valid measured wheel state
      ↓
State Estimation
```

如果 feedback 無效：

```text
× 不可以拿 command value 假裝 measurement
```

所以 04 找出的：

```text
Base Feedback Validity Checker
```

自然落在 Base Control responsibility。

不是 State Estimation。

---

### 6. Base Control 的 responsibility boundary

可以先理解成：

```text
S7 Base Control
│
├── Motion Command Execution
│
│   └── differential-drive motion
│
├── Motion Protection
│   ├── command timeout
│   └── motion limits
│
├── Hardware State
│   ├── measured wheel feedback
│   └── feedback validity
│
└── Hardware Safety
    ├── hardware ERROR handling
    ├── safe enable
    ├── stop confirmation
    └── motor disable
```

這仍然不是在決定內部 node 怎麼拆。

只是說這些責任在 system architecture 上屬於同一個底盤控制與安全 boundary。

---

## Step 10 候選結論

我建議：

```text
S7 Base Control
```

**保留為獨立 subsystem。**

簡單講：

> Navigation 負責「是否還要移動」；Base Control 負責「速度命令如何安全執行，以及底盤是否真的處於可控、安全的物理狀態」。

到這裡，Step 3 提出的 **7 個 subsystem boundary 已全部逐一檢查完成**：

```text
S1 Robot Description
S2 Perception
S3 State Estimation
S4 Mapping
S5 Localization
S6 Navigation
```

## 05 - Step 13：檢查整體 Control Flow / Ownership

這一步其實是在問：

> **除了資料有沒有接上之外，誰有權「啟動、停止、決定下一步」也要清楚。**

可以把它理解成：

```text
Data Flow
→ 東西從哪裡來、送到哪裡

Control Flow
→ 誰決定現在該做什麼
```

兩者不一樣。

---

### 1. Mapping Mode 的控制權

建圖時：

```text
使用者
  ↓
啟動 Mapping
  ↓
Mapping subsystem
  ↓
建立 / 更新地圖
  ↓
使用者結束
  ↓
儲存 Map Package
```

這裡的主要 owner 很清楚：

```text
Mapping
```

Perception 和 State Estimation只是提供資料，不決定「建圖開始或結束」。

所以：

```text
Mapping = mapping task owner
```

---

### 2. Navigation Mode 的控制權

導航時：

```text
使用者
  ↓
Navigation Target
  ↓
Navigation
```

接下來：

```text
Target validation
Route selection
First Mile
On Route
Last Mile
Goal completion
Result
```

都屬於同一個 navigation task。

所以：

```text
Navigation = navigation task owner
```

這點很重要。

不能變成：

```text
Route Server 決定一部分
Planner 決定一部分
Controller 決定一部分
某 custom node 再決定一部分
```

而沒有一個 system-level owner。

成熟元件可以執行工作，但 **Navigation subsystem 必須擁有整體 orchestration responsibility**。

---

### 3. Localization 沒有 Navigation control authority

Localization 只負責：

```text
「我現在在哪裡」
```

即使定位結果暫時不好，它也不應自行：

```text
取消 Navigation
切換 route
停用 Base Control
```

它只提供自己的狀態與成熟元件原生 failure。

接下來怎麼處理，是 Navigation 或更底層 safety responsibility。

所以：

```text
Localization
→ information owner

Navigation
→ navigation decision owner
```

---

### 4. Navigation 也沒有 Hardware control authority

Navigation 可以說：

```text
「我要前進」
「我要停止」
```

但不能直接決定：

```text
motor enable
driver disable
hardware fault recovery
feedback 是否可信
```

所以控制鏈應該是：

```text
Navigation
    ↓
desired motion
    ↓
Base Control
    ↓
safe executable motion
    ↓
hardware
```

這裡的 authority boundary 是：

```text
Navigation
→ 任務與運動意圖

Base Control
→ 底盤是否允許及如何安全執行
```

---

### 5. 最重要的 ownership 可以先整理成這樣

```text
Mapping
→ Mapping task owner

Localization
→ map-relative pose owner
→ map → odom owner

State Estimation
→ planar odometry owner
→ odom → base_footprint owner

Navigation
→ Navigation task owner
→ route / stage orchestration owner
→ Navigation result owner

Base Control
→ base motion execution owner
→ measured wheel-state validity owner
→ hardware safe state owner
```

這樣 architecture 不會出現「兩個地方都以為自己是最後決策者」。

---

目前 7 個 subsystem 的 control ownership 是可以閉合的。

最核心的 chain 是：

```text
使用者
   ↓
Navigation
   ↓
motion intent
   ↓
Base Control
   ↓
hardware
```

旁邊則是：

```text

State Estimation
Mapping
Localization

```

提供 Navigation 和 Base Control 所需要的資料與模型，但**不搶 task-level control authority**。

## 05 — Step 14：檢查 Failure Propagation / Stop Ownership

這一步其實是在問：

> **某個 subsystem 出錯時，誰負責「回報錯誤」，誰負責「停止任務」，誰負責「讓底盤真的安全停下來」？**

這三件事不能混在一起。

---

### 1. 先分成三層

可以把 failure 處理想成：

```text
底層發現問題
    ↓
上層決定任務是否失敗
    ↓
底盤執行停止 / 安全處置
```

例如 Navigation path tracking 失敗：

```text
Controller / Planner failure
        ↓
Navigation 判定任務無法繼續
        ↓
Navigation 結束 task
        ↓
要求停止移動
        ↓
Base Control 執行停止
```

---

### 2. Mapping failure

Mapping Mode 比較簡單。

例如：

```text
LiDAR / odometry 不可用
Map save 失敗
Map read-back 失敗
```

責任關係應該是：

```text
下游 mature component 回報 failure
        ↓
Mapping subsystem
        ↓
Mapping task Failure
        ↓
回報使用者
```

也就是：

```text
Mapping = 最終 Mapping Result owner
```

Perception 或 State Estimation 不直接對使用者宣告：

> 「UC-001 失敗。」

它們只是回報自己的 failure/state。

---

### 3. Navigation failure

Navigation 的情況更多：

```text
Target invalid
Localization input unavailable
Planning failure
Tracking failure
Route blocked
Route reselection exhausted
Fallback unavailable
Cancel
```

最後都必須收斂到：

```text
Navigation
    ↓
Success / Failure / Canceled
```

所以：

```text
Navigation = 最終 Navigation Result owner
```

---

### 4. 但 Navigation Failure 不等於 Hardware Fault

例如：

```text
找不到 route
```

這是 Navigation failure。

它不代表：

```text
motor driver 壞掉
```

所以不能把所有 Navigation failure 都升級成 hardware disable。

正常情況應該是：

```text
Navigation failure
      ↓
停止 navigation task
      ↓
停止要求移動
      ↓
Base Control 讓底盤停止
```

不一定要：

```text
disable motor driver
```

---

### 5. Hardware fault 則相反

如果 Base Control 發現：

```text
driver alarm
communication failure
invalid hardware feedback
hardware interface ERROR
```

那 Base Control 本身就有權處理底盤安全。

例如：

```text
Hardware fault
     ↓
Base Control
     ├── stop / reject motion
     ├── controller affected
     └── expose fault
```

然後 Navigation 得知底盤已無法正常運動後：

```text
Navigation
     ↓
Navigation Failure
```

所以方向是：

```text
Base Control fault
      ↓
Navigation task failure
```

不是 Navigation 指揮 Base Control：

> 「請把這個 hardware fault 當成 fault。」

---

## Step 14 候選結論

我建議正式採用三層 ownership：

```text
Component / Subsystem
→ 發現並回報自己的 failure

Task Owner
→ Mapping / Navigation 決定整體 task 結果

Base Control
→ 負責實際底盤停止與 hardware safety
```

簡單講：

> **誰發現錯誤，不一定是誰決定整體任務失敗；誰決定任務失敗，也不一定是誰負責硬體安全停止。**

這一步其實是在問：

```text

        ≠
Localization 一定可以正常工作
```

```text
Map
LaserScan
Odometry
TF
```

所以 05 不應把：

> node 已經啟動

直接當成：

> subsystem ready。

我們真正關心的是 **dependency 是否成立**。

最底層大致是：

```text
Robot Description
Perception
Base Control
      │
      ▼
State Estimation
```

原因很直觀。

State Estimation 需要：

```text
Base Control
    ↓
wheel feedback

Perception
    ↓
IMU / LiDAR-derived odometry input

Robot Description
    ↓
frame relationships
```

因此功能依賴是：

```text
Robot Description ─┐
Perception ─────────┼→ State Estimation
Base Control ───────┘
```

這不代表一定要按照固定秒數依序 launch。

只是代表：

> State Estimation 要正常產生結果，這些輸入必須成立。

---

### 3. Mapping Mode 有自己的 dependency chain

UC-001 需要：

```text
Robot Description
       │
Perception
       │
State Estimation
       │
       ▼
    Mapping
```

簡化就是：

```text
Sensors + Odometry
        ↓
     Mapping
```

**Localization 不需要參與 UC-001。**

Navigation 也不需要參與。

所以不應設計成：

```text
Localization 沒 ready
      ↓
整個系統不能 Mapping
```

這會產生錯誤依賴。

---

### 4. Navigation Mode 的 dependency 比較完整

UC-002 則需要：

```text
Robot Description
Perception
Base Control
      ↓
State Estimation
      ↓
Loaded Map
      ↓
Localization
      ↓
Navigation
```

Navigation 另外需要：

```text
Route Graph
Station Catalog（Station Target 時）
```

所以概念上：

```text
          Map
           │
           ▼
Odometry → Localization ← Perception
                │
                │ map-relative localization
                ▼
Route Graph → Navigation ← Navigation Target
                │
                ▼
           Base Control
```

---

### 5. Station Catalog 是條件式 dependency

這點值得特別保留。

如果使用者給：

```text
Station A01
```

Navigation 必須使用：

```text
Station Catalog
```

但是如果使用者直接給：

```text
Goal Pose
```

Station Catalog 根本不需要參與。

所以不能定義成：

```text
沒有 stations.yaml
      ↓
Navigation Mode 永遠不能使用
```

正確的是：

```text
Station Target
      ↓
需要 Station Catalog

Goal Pose Target
      ↓
不需要 Station Catalog
```

這與目前 01-03 的語意一致。

目前我認為 **不需要**。

```text

├── 啟動 Mapping
├── 啟動 Localization
```

```text

```

> 「目前 odometry 座標系相對 Map 在哪裡。」

所以：

```text

    ↓
```

所以：

```text

    ↓
authoritative odom → base_footprint
```

```text

    ↓

```

```text

不一致
定位不穩
```

> **每一段 dynamic TF 只能有一個 authoritative producer。**

其他 component 可以計算自己的 pose / odometry，但不能同時搶 TF ownership。

## 05 — Step 17：檢查 `cmd_vel` Command Chain

這一步其實是在問：

> **Navigation 只負責提出運動意圖；Base Control 擁有最後的運動執行權。**

---

### 1. 最基本的命令鏈

概念上應該是：

```text
Navigation
    ↓
desired velocity
    ↓
Base Control
    ↓
safe / limited velocity
    ↓
diff-drive execution
    ↓
Motor Driver
```

簡單講：

```text
Navigation
→ 「我想這樣走」

Base Control
→ 「這個命令能不能安全執行，以及實際執行多少」
```

---

### 2. Navigation 可以做什麼？

Navigation 可以根據：

```text
Path
Obstacle
Current Pose
Controller
```

算出例如：

```text
linear.x = 0.4 m/s
angular.z = 0.3 rad/s
```

它也可以因為：

```text
Cancel
Path failure
Route failure
Goal reached
```

停止要求移動。

但 Navigation 不應該決定：

```text
driver 是否 enable
feedback 是否有效
hardware fault 時是否允許繼續
command timeout 怎麼保護
最終 operational limit 是否被違反
```

---

### 3. Base Control 為什麼必須有最後否決權？

假設 Navigation 還在送：

```text
0.4 m/s
```

但 Base Control 發現：

```text
Motor alarm
Communication fault
Invalid wheel feedback
Driver not ready
```

這時不能因為 Navigation 說要走，就照走。

正確關係是：

```text
Navigation command
       ↓
Base Control safety gate
       ↓
允許 → 執行
拒絕 → 不執行 / 停止
```

也就是：

> **上游可以要求移動，但底盤層永遠可以因安全條件拒絕非零運動。**

這和 SYS-030 很一致。

---

### 4. Motion Limits 放在哪裡？

SYS-028 要求：

```text
linear velocity
angular velocity
acceleration
deceleration
```

不能超過 operational limits。

這些限制可能技術上由成熟 component 實現，但 architecture ownership 應該歸在：

```text
Base Control
```

因為這是：

> **底盤允許執行的運動 envelope。**

Navigation controller 可以自己產生合理速度，但不能成為唯一 safety guarantee。

所以概念上：

```text
Navigation generated command
        ↓
Base motion limits
        ↓
Executable command
```

---

### 5. Command Timeout 也屬於 Base Control

如果 Navigation 突然停止更新命令：

```text
Navigation
    ↓
最後一筆非零 cmd
    ↓
……沒有新 command……
```

Base Control 不能一直維持舊命令。

必須：

```text
command age > timeout
        ↓
stop
```

所以 SYS-027 的 ownership 仍然很清楚：

```text
Base Control
```

不是 Navigation。

```text

→ motion command producer

Base Control
→ motion command admission / limiting / timeout / execution owner
```

也就是：

```text

    ↓
desired motion
    ↓
Base Control
    ├── safety gate
    ├── motion limits
    ├── timeout protection

    ↓

```

```text

      ↓
Canonical Goal Pose
      ↓
Route-assisted strategy
      ↓
First Mile
      ↓
On Route
      ↓
Last Mile
      ↓
Final Goal Completion
      ↓
Navigation Result
```

重點是：

> 這不是三個獨立 navigation task，而是一個 navigation task 裡的三個 stage。

### 2. First Mile 完成，不代表 Navigation 成功

例如：

```text
Current Pose
    ↓
First Mile
    ↓
Route Entry
```

> **可以進入下一個 stage。**

不能因為 Nav2 某個 `FollowPath` action 回 `SUCCEEDED`，就直接對使用者回：

```text
Navigation Success
```

正確是：

```text
First Mile SUCCEEDED
        ↓
Navigation orchestration
        ↓
切換到 On Route
```

---

### 3. On Route 也一樣

```text
Route Entry
    ↓
On Route
    ↓
Route Exit
```

到達 Route Exit 只代表：

```text
On Route stage completed
```

接下來還要判斷：

```text
Route Exit == Canonical Goal Pose ?
```

如果不是：

```text
進入 Last Mile
```

如果已經是：

```text
Last Mile = zero-length / skipped
```

---

### 4. Zero-length stage 怎麼處理？

這是目前 requirement 已經明確允許的。

例如機器人本來就在 route entry：

```text
Current Pose ≈ Route Entry
        ↓
First Mile 不需要執行
        ↓
直接進 On Route
```

同理：

```text
Route Exit ≈ Goal
        ↓
Last Mile 不需要執行
        ↓
直接進 Final Goal Completion
```

這種情況應該視為：

```text
stage not required
```

而不是：

```text
planning failed
```

---

### 5. 誰負責 stage transition？

我建議 ownership 很明確：

```text
Navigation subsystem
    ↓
Stage Orchestration Owner
```

它負責判斷：

```text
First Mile 要不要執行
First Mile 完成後去哪
On Route 是否完成
是否需要 route reselection
Last Mile 要不要執行
何時進入 final completion
```

```text
「執行目前交給我的這一段工作」
```

它們不擁有整體 navigation task state。

---

```text
├── owns overall task
├── owns stage state
├── owns stage transition
└── owns final result
```

```text

On Route
Last Mile
```

只是同一個 task 的執行階段，不是獨立 subsystem，也不是獨立使用者任務。

這一步其實是在問：

> **目前選的 route 走不下去時，系統是直接失敗，還是先換一條 Route Graph 路徑？什麼時候才算真的沒有路可走？**

先看一般流程：

```text
Current Pose
    ↓
選出 Route A
    ↓
First Mile
    ↓
On Route
    ↓
Last Mile
    ↓
Goal
```

只要 Route A 可以安全完成，就不需要做其他事情。

---

### 2. Route A 中途被擋住

例如：

```text
Route A
───────X──────→ Goal
       障礙
```

這時不能立刻：

```text
Navigation Failure
```

因為 requirement 已經要求：

> route-assisted alternatives 要先用盡。

所以應該：

```text
目前 route 無法繼續
      ↓
Navigation 重新評估 Route Graph
      ↓
存在 Route B ?
   ├── Yes → 改走 Route B
   └── No  → 再判斷 fallback boundary
```

---

### 3. Route reselection 是 Navigation 的責任

這不是 Controller 自己決定的。

Controller 可能只會說：

```text
「這條 path 我追不下去了」
```

Navigation 才決定：

```text
「那我要不要重新規劃？」
「要不要換 route？」
「是不是已經沒有 route-assisted solution？」
```

所以：

```text
Controller / Planner
→ 回報 execution failure

Navigation
→ 決定 reselection / task termination
```

---

### 4. 哪些情況才進入 Fallback Boundary？

目前 03 已定義四類：

```text
1. Current Pose 接不上任何 route entry

2. Route Graph 沒有通往 Goal 的可用 route

3. On Route 被阻塞，
   而且 route reselection 也失敗

4. 找得到 route，
   但所有 route exit 都無法安全 Last Mile 到 Goal
```

這四種的共同意思是：

> **route-assisted navigation 已經真的走不通。**

---

### 5. v0.1 這時不能改成自由導航

這點要非常清楚。

如果 route-assisted solution 不存在：

```text
Route-assisted exhausted
        ↓
Free-space Fallback eligible
```

未來版本可能：

```text
        ↓
完整 free-space navigation
```

但 v0.1 明確是：

```text
Route-assisted exhausted
        ↓
Fallback eligibility detected
        ↓
不執行 free-space fallback
        ↓
停止 navigation task
        ↓
要求底盤停止
        ↓
回報 Free-space Fallback unavailable
```

---

### 6. 不是所有 failure 都算 Fallback

例如：

```text
Station ID 不存在
Map 載入失敗
Localization 不可用
Route Graph 檔案壞掉
Goal Pose 無效
```

這些不能說：

> 「Route 不行，所以進 fallback。」

它們分別是自己的 failure boundary。

所以：

```text
Target invalid
→ Target failure

Map load failed
→ Resource / Mapping failure

Localization unavailable
→ Localization failure

Route-assisted 本身真的不可成立
→ Fallback eligibility
```

這個分類很重要。

---

```text
嘗試 route-assisted alternative
        ↓

   ├── Yes → 繼續 Navigation

        ↓

        ↓
```

簡單講：

## 05 - Step 20：檢查 Goal Completion

這一步其實是在問：

```text

On Route 完成
→ 只代表到達 Route Exit

Last Mile 完成
→ 只代表走完最後一段 path
```

這些都只是 stage result。

不能直接變成：

```text
Navigation Success
```

---

### 2. 真正的成功條件

最後要確認：

```text
Current Pose
    ↓
符合 Goal position tolerance
    +
符合 Goal orientation tolerance
    +
底盤已停止
    ↓
Navigation Success
```

也就是：

> **位置到了、方向到了，而且真的停住。**

這承接 SYS-016。

---

### 3. 為什麼「path 執行成功」還不夠？

因為 controller 回報某段 path 完成，只代表：

> 這段 execution 已完成。

但整體 Navigation 的 authoritative target 是：

```text
Canonical Goal Pose
```

所以 Navigation 必須以最終 target 為準，而不是某個中間 stage endpoint。

---

### 4. Zero-length Last Mile 也不例外

如果：

```text
Route Exit ≈ Canonical Goal Pose
```

那 Last Mile 可以不執行。

但仍然要：

```text
Route Exit
   ↓
Final Goal Completion Check
   ↓
Position + Orientation + Stopped
```

不能因為 Last Mile skipped 就直接成功。

---

### 5. 誰負責判定？

Architecture ownership 應該是：

```text
Navigation
→ owns final Navigation Success decision
```

但成熟 Nav2 元件負責提供實際 goal-checking behavior，例如：

```text
StoppedGoalChecker
```

所以責任關係是：

```text
Nav2 mature goal checker
→ 判斷 final pose / stopped condition

Navigation orchestration
→ 將 final completion result
   轉成整體 Navigation Success
```

---

```text
→ stage transition
```

這一步其實是在問：

```text id="89gvql"

├── Success
├── Failure
└── Canceled
```

不要在 05 再創造很多 system-level result type。

例如：

```text id="6m4tg7"

PLANNER_FAILED
CONTROLLER_FAILED
LOCALIZATION_FAILED
...
```

這些可以作為 failure reason / native error detail，但最終狀態仍然是：

```text id="ti06jr"

```

---

### 2. Success 的來源

只有 Step 20 的最終條件成立：

```text id="me597z"
Canonical Goal reached
        +
orientation satisfied
        +
robot stopped
        ↓
Success
```

中間 stage 成功不能直接變成整體 Success。

---

### 3. Failure 的來源

很多底層問題最後都可能收斂成 Failure，例如：

```text id="drzjdf"
Target invalid
Planning failure
Tracking failure
Localization unavailable
NO_ROUTE_ASSISTED_SOLUTION
Base Control fault
```

資料流是：

```text id="jfbm4t"

        ↓
Navigation 無法繼續 task
        ↓
Navigation Failure
        ↓
保留可取得的原生 failure reason
```

也就是：

> **Navigation 統一結果，但不要吞掉底層原因。**

---

如果使用者主動：

```text id="0h3cfl"
Cancel Navigation
```

正常流程是：

```text id="w8wsuc"

     ↓
Navigation 停止目前 task
     ↓
停止 active stage / child actions
     ↓
停止要求移動
     ↓
等待 cancellation 完成
     ↓
Canceled
```

不能把它回成：

```text id="l76z23"
Failure
```

因為：

```text id="ljxf3g"
Failure
→ 系統想完成，但做不到

Canceled
→ 使用者要求不要再完成
```

語意完全不同。

---

### 5. Cancel 也不能等同於「底盤已安全停妥」

這和前面 Step 14 / 17 一樣。

Navigation 做：

```text id="ce77gg"
取消 task
↓
停止 motion request
```

Base Control 負責：

```text id="pd5ehd"
command timeout / zero command
↓
實際底盤停止
↓
hardware safety
```

所以：

> Navigation cancellation 是 task semantics；Base Control stop 是 physical execution semantics。

兩者相關，但不能合併成同一責任。

---

## Native lifecycle enable slice

Manual p33 specifies ISTOP0/data0, SVON6/data0 and SVOFF7/data0 when01-10 is nonzero; SVOFF may implicitly reset alarms. Manual p38 read index12 is target speed. The adapter pre-reads valid no-alarm feedback and target speed, requests ISTOP, requires fresh verified target0, then requests SVON once. It polls readiness bounded by the explicit enable timeout, verifying target0 throughout. An ignored ISTOP with stale target prevents SVON. Any post-enable failure returns ERROR and attempts bounded zero/off cleanup only with fresh no-alarm proof. Captured alarms/fault5 latch against SVOFF; read failure also prevents it. There is no automatic enable retry or explicit reset. A fault arising between proof and SVOFF cannot be atomically excluded, so this is not a universal no-reset guarantee.

Deactivation/shutdown uses typed success/detail cleanup outcome: ISTOP acknowledgement, fresh no-alarm proof, SVOFF acknowledgement, and inhibited readback are all required for SUCCESS. Any unavailable acknowledgement/readback returns ERROR. Error handling requests ISTOP and retains the cause. Inhibited readback after SVOFF is a protocol inference, not independent physical-stop evidence.

RED→GREEN public native workflow slices: stale target safely cleared before SVON; bounded readiness transition; ignored stop with stale target never enables; unavailable enable transition attempts safe off; native deactivation initially left Servo ON, corrected to stop/off; alarm during enable preserved without SVOFF reset. Public tests also verify failed SVOFF produces native transition failure and launch SIGINT shutdown sends stop/off. All use external PTY peer and native lifecycle APIs, never physical devices.

`config/rwf.commissioning.yaml` retains confirmed geometry/directions/transport but explicitly identifies firmware as UNIDENTIFIED. Engineering choices:20Hz controller,50ms per-transaction response timeout,0.3s command timeout and enable deadline,150RPM motor ceiling,0.03m/s and0.10rad/s limits.
